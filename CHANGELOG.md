## [Unreleased]

### Added

**A hook that blocks NEW em-dashes in Markdown, since the AGENTS.md rule against them was never enforced:**
- `baseline/hooks/block-new-em-dashes.sh`, registered `PreToolUse` on `Edit|Write|MultiEdit` in THIS repo's own `.claude/settings.json`. The repo had 516 em-dashes across 49 Markdown files (excluding CHANGELOG.md), 289 of them in `baseline/skills/`, all written before this rule had a hook behind it: the decision here is to leave that debt alone (rewriting an em-dash sentence needs a human's judgment about phrasing, and most of those files ship into every adopting project) and gate the diff instead of the tree. The check is a before/after em-dash count on the SAME file across the same Edit/Write/MultiEdit call: editing a line that already had one, moving text, or deleting one all pass; a net increase blocks, with a message pointing at rewriting the sentence, not swapping the character for a double hyphen. Only U+2014 is covered; U+2013 (en-dash) is deliberately out of scope, since it has legitimate uses in this repo's prose (numeric ranges) that AGENTS.md's rule was never aimed at. Scoped to `.md` files only. Deliberately NOT added to `install-harness.sh`'s portable set or `install.sh`'s `REPO_HOOKS`: this is a style preference of this repo, not something an adopting project should inherit by linking the harness. `AGENTS.md`'s convention line and `CLAUDE.md`'s "Hooks registered" section updated to describe the new, honest scope. Tests in `baseline/hooks/tests/block-new-em-dashes.test.sh`.

**A fourth rule in `git-workflow.md`, from a stacked PR that merged into a dead branch:**
- `baseline/rules/git-workflow.md` gains "Merge a stacked PR by deleting its branch". A PR whose base is another feature branch only gets retargeted onto the integration branch when the PR below it is merged **with its branch deleted**. Without that, the top PR merges into a branch nobody will merge again: the merge succeeds, the PR reads *Merged*, and the content never reaches the integration branch. Measured on this repo, 2026-09-11: #45 was stacked on #44's branch, #44 was merged without deleting `fix/install-link-docs-and-scripts`, #45 landed in that dead branch, and it had to be reapplied in #47. Neighbouring case in the same rule: #42 was merged while GitHub still showed an older head and its last commit (`f81a2f4`) never reached `main`, reapplied inside #44. The rule ships the two pre-merge checks that catch both, `gh pr view <n> --json baseRefName,headRefOid` and `gh pr merge <n> --match-head-commit <sha>`.

**`script/setup` and `script/test` — Scripts to Rule Them All, called when a project has them:**
- New guide `docs/guides/script-setup-and-test.md`: what a good `script/setup` (fixes the runtime first, installs, provisions the local env file from a versioned example only if it's missing and never invents a secret, runs codegen, ends by running `script/test` and recording the baseline) and `script/test` (the actual gate; never a command that rewrites files as a side effect, e.g. lint with `--fix`; run at least once under a cheap environment variation like `TZ=UTC`) do. Stack-agnostic, with a minimal Node example of each.
- `spec-worktree.sh` runs the new worktree's `script/setup`, if executable, right after provisioning the gitignored locals — taking the worktree from "created" to "ready to work in" in one command. `--no-setup` skips it. On failure the worktree is **never removed** (exit code 3): it prints where the worktree is and that the environment didn't come up, and leaves the branch work intact for a manual rerun. A repo without `script/setup` is unaffected — the step is a no-op, not a warning. `spec-worktree` SKILL.md documents the step and the flag.
- `verify-before-done` now checks for an executable `script/test` first: if the repo has one, it **is** the gate — run it instead of rediscovering commands from `AGENTS.md`/`package.json`. Same split for `script/setup` on the install/codegen side. Without either, the skill falls back to today's discovery-based flow.
- `analyze-codebase` flags a missing `script/setup`/`script/test` as a report recommendation when adopting the harness on an existing project — it does not write them, since only the team knows what "ready" and "verified" mean for that repo.

Why: on njord-back, the same ~15 lines of environment setup (Node version, that `yarn lint` runs `--fix` and can't be the gate, which command is the actual gate) got repeated across 53 subagent briefings — all of it already written in `AGENTS.md`, with nothing executing it. Two worktrees (install, codegen, baseline) had to be assembled by hand, twice. The fix is the well-known GitHub convention: project-owned, committed, executable scripts at the repo root that a human, CI, and an agent all run the same way. The harness does not generate them — it only calls them when they exist, and says so when they don't.

**Three gaps recovered from njord-back's own copy of `.claude/` before it stops vendoring one and adopts the harness link:**
- **Specialist routing map.** njord-back's customised `/orchestrate` (before it was replaced by this template's stack-agnostic driver) routed each task class to a specialist via a `specialists:` map in its own knowledge catalog; nothing in the template ever read that map, so it would have gone silent the moment the old `orchestrate.md` — its only reader — was deleted. `orchestrate/SKILL.md` Step 1 and `wave/SKILL.md` now route a cluster through the project's own routing map when its context declares one (a `specialists:` key in an imported catalog, or an equivalent table in `AGENTS.md`/`CLAUDE.md`), falling back to today's pick-by-stack behavior otherwise, and note that a plugin-provided agent is namespaced (`<plugin>:<agent>`) so the map's name has to match what the Agent tool actually accepts.
- **"The three principles" pointer, dangling since the file never shipped.** `orchestrate/SKILL.md` and `skill-architect/SKILL.md` both cited `.claude/README.md` for the three principles (one home per topic, rule vs. skill, one owner per document) and for the layer model — a file `install-harness.sh` never delivers and the harness's own checkout does not have either, so every one of those pointers was dead on arrival, in every project that ever linked this harness. The principles section moves to `baseline/docs/principles.md`, delivered as `.claude/docs/harness/principles.md` and now covered by `check-index.sh`'s dangling-pointer check; `baseline/README.md` keeps the layer table and points to the new file for the principles. Every other `.claude/README.md` mention found in `baseline/` (`dispatching.md`, `skill-architect/SKILL.md`, `check-index.sh`'s own drift message) corrected to match.
- **Hooks fail open in silence when no Python is on `PATH`.** The guard hooks (`block-secrets.sh`, `protect-main.sh`, `protect-critical.sh`) and the observability hooks (`log-edit.sh`, `log-agent.sh`) all extracted the tool payload with `python3`, which is absent or a broken alias on some Windows shells where only `python` is installed — recovered from njord-back's own `require-tests-before-push.sh` (PR #819), which had already hit this and added a fallback. All five hooks now try `python3` then fall back to `python`. The three guards additionally print a loud stderr warning and let the call through when neither is present, rather than blocking every Bash/Edit/Write call on that machine — a guard that blocks unconditionally trains its own users to disable the whole hook, which protects nothing; failing open with a visible warning leaves the machine exactly as unprotected as before hooks existed, not worse. The two observability hooks only needed the fallback, since they never block. Verified with a PATH shimmed to expose only `python` (guards still block, using the fallback) and a PATH with neither binary (guards warn on stderr and exit 0; observability hooks exit 0 without writing a log line).

**The installer only ever linked three of the five things it pointed at:**
- `install-harness.sh` now also links `.claude/docs/harness` → `baseline/docs` and `.claude/scripts/harness` → `baseline/scripts`, the same namespaced-subdirectory pattern already used for `rules/harness` — so a project's own `.claude/docs/libs/` (how *this* project uses each lib) or a script it wrote itself under `.claude/scripts/` never collides with what the harness provides. Covered everywhere the other three links already were: normal install, `--adopt`, `--unlink`, `--status`, `--dry-run`, the Windows copy fallback (`.harness-copy` marker), and `.git/info/exclude` (resolved via `git rev-parse --git-path`, correct inside a worktree). `check-baseline.sh`'s broken-link and stale-copy checks, and `spec-worktree.sh`'s carry-the-links-into-a-new-worktree step, extended to the same two entries.
- The gap was real, not cosmetic: `baseline/` pointed at `.claude/docs/...` and `.claude/scripts/...` **44 times across 27 files** (`/spec-worktree` calling its own script, `orchestrate` and `delegation.md` citing `dispatching.md` and `context-engineering.md`, `harness-report` citing `harness-baseline.md`, and so on) — every one of them dangling in a project that adopted the harness through the installer alone. Rewritten to the `harness/` namespace wherever the target is something `baseline/docs` or `baseline/scripts` actually provides. Two pointer shapes are deliberately left as-is: `.claude/scripts/check-snapshot.sh` (copied directly into a project by `install.sh`, per repo, on purpose — never delivered by the harness link) and `.claude/docs/libs/...` (project-owned content by definition; `baseline/docs/libs/example-lib.md` is a template to copy elsewhere, not something the harness link exposes at that path).
- The template's own `.claude/` had the identical bug: it only self-links `skills`, `agents` and `rules/harness` with committed relative symlinks, so `baseline/rules/delegation.md`'s own `.claude/docs/dispatching.md` reference was broken in the harness's own repo. Fixed with two more committed relative links, `.claude/docs/harness → ../../baseline/docs` and `.claude/scripts/harness → ../../baseline/scripts`, matching the existing `rules/harness` pattern.
- `check-index.sh` gains a **fourth class of drift**: a `.claude/docs/...` or `.claude/scripts/...` mention in a rule, skill, agent or script that does not resolve as a file from the repo root — exactly the failure mode above, which none of the first three classes could see since nothing dereferences prose. `--strict` exits 1. Verified two ways: run against this repo's own tree it reports 0; run against a copy of `main` before this fix, it reports **35 dangling pointers** across the same files enumerated above (proof the check catches the bug it was written for, not just that it passes after the fact).
- Verified end to end in throwaway repos: a fresh project with no `.claude/` gets all five links, and of the 22 `.claude/docs`/`.claude/scripts` mentions found inside the linked content, 18 resolve as plain files and the remaining 4 are the two deliberate exceptions above (they resolve once `install.sh` runs or the project writes its own lib doc, not through the harness link). A second project with its own `.claude/docs/libs/foo.md` and `.claude/scripts/meu.sh` keeps both untouched after install, `--unlink` returns the tree to exactly its pre-install state (`git diff --stat HEAD` empty), and `--dry-run` changes nothing on disk either way.

**What the driver `/orchestrate` replaced did better, ported in — review per cluster, falsifiable tests, an environment-varied branch review, findings tracked:**
- `/orchestrate` Step 3 item 4: `code-reviewer` now runs **once per cluster**, scoped to the files that cluster's specialist reported touching, all dispatched in one message — not once for the whole wave. `tester` stays wave-wide: in the A/B below it wrote nothing in 16 of 16 dispatches under the old driver (1.84M tokens spent confirming coverage it already had), so duplicating it per cluster buys nothing a class-to-gates matrix doesn't already give it. `/wave`, `docs/workflows/feature-pipeline.md` and `CLAUDE.md` updated to match. `baseline/agents/code-reviewer.md`, `baseline/agents/reviewer.md`, `baseline/skills/write-spec/references/tasks-template.md`, `baseline/docs/superpowers.md` and `docs/reference/spec-driven.md` now say which cadence applies when — per cluster under `/orchestrate`, per phase when `tasks.md` is worked by hand.
- `/orchestrate` Step 3 item 1 (implementation handoff): clusters producing logic or tests must now prove their central assertions kill a mutation — applied to a copy in scratchpad/tmp with the import redirected, never the tracked file — name denominators and arithmetic boundaries as an explicit case, and prove any "equivalent mutant" claim by construction against the real call site, never by the parameter's declared type (a query-string or untransformed-DTO value routinely arrives outside it).
- `baseline/agents/reviewer.md`: before sign-off, re-runs the suite under at least two timezones (one UTC, one at a distant offset), two locales, the runner's serial mode, and random test order, when supported — never trusts the author's own green.
- `baseline/agents/code-reviewer.md`, `reviewer.md`, `tester.md`, `baseline/docs/dispatching.md`: verification agents write only their own deliverable — never a tracked file outside it, not even temporarily for a mutation check, and never `tasks.md`/`spec.md` (a reviewer suggests the edit in text; the orchestrator makes it).
- `baseline/rules/specs.md`: `deviations.md` gains a `finding` status — a production defect a test reveals, out of scope for the task. It does not block the run (only `needs decision` does) but surfaces in the PR's new "Findings outside scope" section (`/orchestrate` Step 4) and in `/handover`'s and `/status`'s open-decisions reporting.

Why: an A/B on njord-back (same 16-task spec, same instrument, only the orchestration driver changed) measured the current `/orchestrate` at 1.78M tokens / 8 dispatches against the 53-line driver it replaced at 7.71M / 53 (4.34x) — the cluster shape confirmed. But the old driver's per-task review caught real assertion gaps in 3 of its first 4 tasks that this driver's one wave-wide review missed, and its branch reviewer, by running under a different timezone than the author, caught 6 tests failing under `TZ=UTC` that neither the author's green nor the gate ever saw. Full numbers and what the A/B does not prove: `baseline/docs/harness-baseline.md`, section "2026-09-10 — A/B".

**Delegation and dispatch discipline** — from telemetry on a real project running this template (22 sessions, 54 subagent dispatches):
- `.claude/rules/delegation.md` (always loaded) — the main thread coordinates, specialists implement. The rule previously existed only inside `/orchestrate`, a command that ran twice in 729 prompts; meanwhile 71% of `Edit` calls happened in the main thread while `Grep`/`Glob` were 100% delegated. Also added to `AGENTS.md` non-negotiables.
- `.claude/docs/dispatching.md` — opens with the **six topology shapes** (pipeline, fan-out/fan-in, expert pool, producer-reviewer, supervisor, hierarchical delegation): what each fits, what to watch for, and how to run each with sub-agents, since picking the wrong shape costs more than any mechanic recovers. Catalogue adapted from [revfactory/harness](https://github.com/revfactory/harness) (Apache-2.0). Then the mechanics: parallel means several agent calls **in one message** (measured: 54 of 54 dispatches went out one per message, so the wave plan never actually fanned out); background only for long work collected in the same turn (measured: two dispatches collected 16 days after launch, across a suspended session); never background a gate; concurrency ceiling; diversity over redundancy; agent memory.
- `.claude/rules/specs.md` (`paths: specs/**`) — claims about the current state of the system are verified against code/git when written, never copied from existing prose; a hand-written spec still goes through `spec-reviewer`. Includes the cheapest check for a referenced "pending fix": a `git cherry-pick` that comes back **empty** means the content is already in your base, re-applied under a different PR number. Measured: a follow-ups spec was written from a three-week-old header claiming two tests were failing; they had been fixed and merged under another PR, and the block was ranked priority 1. The defense already existed (`write-spec` hands the spec to `spec-reviewer` to verify claims against the codebase) and was skipped because the spec was written by hand — a guard that only fires on the happy path is not a guard.
- `/wave` command — the low-ceremony half of `/orchestrate`: one batch of independent tasks, dispatched in parallel, gated once, then stop. No spec, no approval table, no PR.
- **`deviations.md`** — a fifth spec-folder artifact, created on demand, for where execution left the agreed plan: assumptions taken, blockers worked around, scope changed mid-flight, phases run straight from `plan.md` instead of as tasks. Distinct from `lessons.md`, which is about the system (*this broke, here is the fix*, promotable to a rule) where a deviation is about this feature's plan (*we agreed X and did Y*, resolved and closed, never promoted). Format and the four things that belong in it are in `.claude/rules/specs.md`; `/orchestrate` and `/wave` append as they go, `/status` lists open entries, `/handover` lifts every `needs decision` into open decisions. Measured: deviations with nowhere to go get narrated inside `tasks.md`, where prose competes with the checkboxes and the next wave plan ignores it — which is how a task file becomes a state dump. Concept adapted from [migoVanDingo/base-template](https://github.com/migoVanDingo/base-template).

**The harness measures itself** — `log-edit.sh`, `harness-report.sh`, `/harness-report`, `.claude/docs/harness-baseline.md`:
- `.claude/hooks/log-edit.sh` (PreToolUse on Edit/Write/MultiEdit/NotebookEdit) appends one line per file edit recording **which thread** made it, main or specialist, to the gitignored `.claude/tool-log.txt`. Thread detection is a heuristic on the payload (a subagent's transcript lives under `subagents/`); when it cannot tell it records `?` and the report counts unknowns separately rather than folding them into either side.
- `/harness-report` and `.claude/scripts/harness-report.sh` turn the two observability logs into the delegation ratio, the dispatch mix, and the unattributed count.
- `.claude/docs/harness-baseline.md` records what was actually measured before the corrections (Edit delegated **29%**, main thread carrying **71%** of tokens, **1.0** dispatches per message, `/orchestrate` run twice in 729 prompts) and states, per correction, which number would confirm it — including the honest possibility that delegation does not move, in which case prose is the wrong mechanism and a sentence will not fix it.

Why this exists: `rules/delegation.md` was written to fix inverted delegation, and the 29% was measured with that rule already in place inside `/orchestrate`. A rule nobody can see being broken decays silently. Making it countable is what gives it teeth — and what lets the four corrections shipped in this release be judged rather than assumed.
**Two quiet failures of the link model, closed:**
- `check-baseline.sh` now warns on a **broken link**. This is the model's worst failure and its quietest: move the harness checkout and every link in every project that opted in resolves to nothing — and Claude Code does not error on that. The skills, agents and rules are simply absent, so a session looks completely normal while running unarmed. The check runs before the staleness report, because a dead link makes that report moot, and it says out loud that silence is the symptom.
- `spec-worktree.sh` now carries the harness links into a new worktree. They are excluded from git, so they exist only in the worktree that created them — a new worktree of a repo that opted in would otherwise start **without** the harness, silently, the same failure by a different route. It points at whatever target the main checkout uses rather than re-deriving it. Verified: a fresh worktree resolves all three links and reports 19 skills.

**Base branch fix recovered from a stale local copy before deletion:**
- `spec-worktree.sh` picked `origin/main` unconditionally as the worktree base. njord-back's own copy of `.claude/` had already fixed this locally in #811 (2026-07-17): resolve `origin/HEAD` first, falling back to `origin/main` then local `main`, so a repo whose integration branch is `develop` — njord-back's — doesn't spawn every worktree from `main` instead. The fix never reached the harness because njord-back vendored a full copy of `.claude/` rather than linking it; it surfaced only when diffing that copy against this repo ahead of dropping it for `install-harness.sh`. Ported into `base_ref()`; the "branch from `main`" wording updated to match in `git-workflow.md`, `spec-worktree/SKILL.md`, `scripts/README.md` and `CLAUDE.md`. Verified against two bare remotes, one defaulting to `develop` and one to `main`, plus the no-`origin/HEAD` fallback.
- Same diff also caught two agent notes njord-back added locally (PR #786) that the harness never received: `codebase-explorer.md` and `researcher.md` both gained a "keep context lean" line pointing at `context-engineering.md`, now ported.

**`install.sh` now sets up a project's context, not the harness** — the split ADR 0003 implies, made real:
- Two commands, two jobs. `./install.sh --to <repo>` delivers what a repository **owns and commits**: `AGENTS.md`, `CLAUDE.md`, `docs/`, `specs/`, `.claude/settings.json`. `./install-harness.sh` delivers the machinery, by symlink, never committed. Before this, `install.sh` copied `.claude/` wholesale because the machinery lived there — it does not any more, so that copy would have delivered almost nothing while implying it had delivered a harness.
- **It also ships the repo-owned guards.** `protect-critical.sh` (lockfiles, applied migrations, generated code) and `check-snapshot-on-session.sh` are guards, not method: they must hold for a teammate who never installed the harness, so they are copied and committed rather than linked — which is precisely why `install-harness.sh` refuses to register them. `check-snapshot.sh` rides along, since the hook calls it.
- The copied `settings.json` is rewritten to reference `.claude/hooks/…` and to list **only** those two. The portable hooks arrive in the gitignored `settings.local.json` when someone links the harness. Without this rewrite a fresh project inherited hook paths pointing at `baseline/`, which exists only in the harness checkout — every hook would have failed silently.

**The harness is linked into the projects you choose** — `baseline/` + `install-harness.sh`:
- The machinery moved from `.claude/` to **`baseline/`** at the repo root. `install-harness.sh`, run from inside a project, symlinks `baseline/{skills,agents}` into that project's `.claude/` and `baseline/rules` into `.claude/rules/harness/`. **Opt-in per repo** — you run it where you want it and nowhere else. `--global` still exists for machine-wide, `--unlink` takes it back out, and `--status` says what is linked.
- **Nothing is committed.** The links go into `.git/info/exclude`, which is per-clone and never leaves the machine, and hooks are merged into the already-gitignored `.claude/settings.local.json` rather than the repo's `settings.json`. A teammate cloning the repo sees no dangling symlink and CI sees nothing at all — so linking a repo you share with other people is safe.
- **Works in a worktree.** The exclude path is resolved with `git rev-parse --git-path` instead of assuming `.git` is a directory — in a worktree it is a *file*, so the old test reported "not a git repo" and silently skipped excluding the links. `info/exclude` lives in the common git dir and is therefore shared by every worktree of the repo; that is harmless (the paths it lists are tracked in the others, and gitignore does not affect tracked files) and the installer says so rather than leaving it as a surprise.
- **Absolute paths**, so there is no sibling-clone assumption: a work repo, a new site and a throwaway experiment all work the same.
- **Rules land in a subdirectory** (`.claude/rules/harness/`) instead of replacing the folder. Rules are discovered recursively, so a repo's own rules keep working alongside — and a project rule still wins over a harness one.
- Updating every project that opted in is `git pull` in the checkout, which retires the `install.sh --update` idea entirely.
- **The six commands are now skills.** A `commands/deploy.md` and a `skills/deploy/SKILL.md` produce the same `/deploy`, so authoring them as skills means nothing depends on a personal `commands/` path that was never verified.
- Every `.pre-harness` file is excluded from git, at any depth — the first pattern missed `.claude/commands/*.pre-harness`, leaving five untracked files in `git status` during an adoption, one `git add -A` away from being committed.
- The installer refuses to clobber: if `.claude/skills` exists and is not its link, it stops and changes nothing rather than deleting what you wrote. **`--adopt`** is the way through for a repo that already has a copied harness: it renames what is in the way to `.claude/<name>.pre-harness` and links over it, and `--unlink` puts it back. It also handles the collisions a directory link cannot — rules and commands **merge** rather than being replaced, so a repo that copied the harness would otherwise load `delegation.md` twice (its own beside the linked one) and keep a stale `commands/orchestrate.md` shadowed by the linked skill; those individual files are set aside too. Measured on a worktree of a real repo: 2 directories and 10 files, all restored by `--unlink` — so the new model can be tried on a real repository and fully reverted with one command. While adopted, git reports the set-aside files as deleted (they are tracked, and the symlink does not expose them); the installer says so and tells you not to commit, **merge or pull** in that state. The merge half is the one that bites: git writes those files back over the links, leaving a real directory beside an orphaned `.pre-harness` that `--unlink` cannot repair because the destination is occupied. Found by merging into an adopted worktree and watching it happen. `protect-critical.sh` and `check-snapshot-on-session.sh` are deliberately left out of what it registers — one knows about lockfiles and applied migrations, the other about a per-repo snapshot, so both belong to a repository's own settings.
- `check-index.sh` now scans `baseline/` and `.claude/` for what a repo owns, and `~/.claude/` for **names only** — without that split, a project that linked the harness would report `/orchestrate` as *indexed but not on disk*.
- `check-baseline.sh` was rewritten for the model it lives in: it reports whether **your checkout** is behind its remote or carries **uncommitted** edits under `baseline/` — which are live in every project that linked it, unreviewed. It does not fetch, so "up to date" means "as of your last fetch", and it says so.

Rationale and the accepted costs: ADR 0002/0003 in the njord marketplace.

**The harness repo can use its own harness again** — a regression from the `baseline/` restructure:
- Moving skills, agents and rules to `baseline/` never linked them back into `.claude/`. Claude Code discovers machinery under `.claude/`, never under `baseline/`, so a fresh session opened in this repository had **no `/orchestrate`, no agents and no rules**. The harness could not use itself.
- Fixed with **committed relative symlinks**, not by running the installer here. Inside its own repository the target is always in the tree, so a relative link is correct in every clone with no install step, and it survives the checkout being moved — which the absolute links the installer writes for consumers do not. Verified on a fresh clone: 19 skills, 7 agents and 5 rules resolve with nothing run, and they still resolve after the clone is moved to a different path.
- `check-index.sh` was reporting every finding **twice**, since `.claude/skills` and `baseline/skills` became the same directory reached by two paths. It now resolves each candidate root with `pwd -P` and keeps only the ones that are new, which also covers a consumer repo whose `.claude/skills` points outside the repo.
- The installer's guard for being pointed at the harness itself said *"it already has baseline/"* — the wrong reason, since having `baseline/` is not the same as being able to use it. It now explains the committed relative links and exits 0, because there is nothing to do rather than something wrong.
**Waves are sliced by cohesion, not by task** — `/orchestrate`, `/wave`, `dispatching.md`:
- Step 1 now groups the unchecked tasks into **a few cohesive clusters of 5-7 tasks**, one specialist per cluster running them **in order in its own context**, instead of one dispatch per task. Clusters must touch disjoint files (they go out together); tasks *inside* a cluster may share files freely, which is what allows a cluster to be cohesive at all.
- The reason is not speed. On an 18-task epic, one-agent-per-task measured **25M tokens / 43m / 0.81** against **10.5M / 18m / 0.95** for ~3 clusters — worse than not dispatching at all. Three findings are now written down, and only the first is intuitive: granularity destroys quality (every dispatch starts from zero and loses the whole); **more workers can leave the main thread fatter**, because each summary returns to it (18 workers used more of it than 7); and the actual win is finishing at **26% of the window instead of 74%**, so the correction rounds are cheap rather than degrading. Eighteen minutes against nineteen is no speed-up.
- Consequently a cluster is told to report **once, not once per task** — a per-task report undoes the context saving that clustering bought.
- `dispatching.md` gains the question that came before its six topology shapes: **whether to dispatch at all** (always for codebase sweeps and research; clustered for long runs; inline for small cohesive work; parallel only when files are genuinely disjoint).

**`jury` — a skill that decides between options:**
- `grilling` builds a decision with a human and `devils-advocate` attacks one already made. Neither **chooses between alternatives**, which is the shape of most expensive calls — and of at least four made in this repo's own history, two of which were reversed within hours.
- Three to five subagents argue **blind in round one** (dispatched in a single message, so context isolation makes anti-anchoring structural rather than a rule to trust), then deliberate on **anonymised** positions, steelmanning before rebutting. A change of mind must cite the argument that caused it; an uncited flip is flagged as bandwagon and the verdict falls back to the blind round at LOW confidence.
- Hard cap of five, because beyond that a panel adds **correlated noise, not signal** — the same effect the dispatch-granularity study found from the other direction.
- Evidence is graded A-D and caps confidence; **there is no abstention**, since refusing to decide is the foreman failing at the only job the panel was convened for. A verdict that changes how the system is built becomes an ADR, carrying its **dissent** and **riskiest assumption** — an ADR that records only the winning argument cannot be re-evaluated later.
- Adapted from `the-jury` by Tech Leads Club (CC-BY-4.0). Their `the-fool` was compared against our `devils-advocate` in the same pass and needed **no changes**: steelman, mode selection, bias scan, 3-5 challenges, engage-before-synthesise and the HIGH/MEDIUM/LOW/PIVOT verdict were all already there.

### Changed

- `/orchestrate` — **Step 3 now executes one wave at a time instead of one task at a time.** The loop was written `for each task: dispatch → gate → review → tick → next`, which is a queue wearing a wave's name: it plans a fan-out in Step 1 and then serializes it in Step 3, paying full latency per task and delivering nothing the plan promised. Measured: 54 of 54 dispatches went out one per message, so no wave plan ever actually fanned out — and the old wording (*"may be dispatched in parallel (background)"*) both permitted the serial path and pointed at background, the mechanism that left two dispatches uncollected for 16 days. Now the whole wave goes out in **one message**, is collected as a barrier, and is gated **once in the foreground**, with the reviewers the wave's classes selected also dispatched together. Gating a batch costs attribution, so a red gate now requires attributing the failure against the files each specialist reported touching — and gating the suspect task alone rather than guessing when that is ambiguous. Waves must contain tasks that touch **disjoint files** (Step 1), which is what makes single-message dispatch safe. Invariant updated: boxes are ticked only on a fresh green gate covering that wave, and a task whose specialist came back short does not inherit a box from its wave-mates.
- `/orchestrate` — new **Step 0 (reconcile)** and a **class-to-gates matrix** in Step 1. Step 0 audits the unchecked tasks against the code and `git log` before any planning, reports the drift in both directions (unchecked-but-done, checked-but-absent) and halts to fix the file: measured, a shipped feature's `tasks.md` sat at 78 open / 12 done and had been copied into three worktrees, so a wave plan would have dispatched a specialist per finished task. Step 1 now classifies each task (schema, logic, API, UI, tests, chore, docs) and selects only the gates that class needs, instead of running `tester` + `code-reviewer` + docs on everything — that uniform ceremony is why the command ran twice in 729 prompts. The build gate never gets skipped, the stricter row wins on ambiguity, and a task whose diff outgrew its class is re-classified before the box is checked. Phase-0 audit and the phase-selection matrix adapted from [revfactory/harness](https://github.com/revfactory/harness) (Apache-2.0).
- `/handover` — now built on **state, not instructions**: it describes what *is true*, never what the next agent *should do*. The `Next steps — the concrete next 1-3 actions` section is gone, replaced by `Current state` and `Not started`; the single forward-looking sentence lives in the closing cut, where it is cheap to discard when wrong. An instruction written now ages worse than a fact — *"implement logout next"* is wrong the moment priorities change, while *"logout is not started"* stays true until someone touches it. Three independent sources converged on this (`davidondrej/skills`, the `_features/` rule in `migoVanDingo/base-template`, and this command's own Step 0), and the command was violating it while teaching it. Also added: **reference, don't duplicate** (stronger than the old "don't paste diffs" — it also rules out restating an ADR's reasoning or a spec's requirements, which creates a second copy that drifts), **frame claims as claims** (mark anything not verified this session as unverified; `.claude/rules/specs.md` applies to a handover too), and the handover is now **printed as a single fenced block** in chat as well as written to the file, since the block is what actually gets carried across the cut. The closing cut template was in Portuguese in an otherwise English template; it is now English. Principles adapted from [davidondrej/skills](https://github.com/davidondrej/skills).
- `/handover` — new **Step 0**: reconcile `tasks.md` against reality before writing the narrative, and check `lessons.md` for a class of failure worth promoting to a rule. Prose and checkboxes are two states of the same file and only one is machine-readable; a handover written over stale boxes documents a fiction that the next wave plan then executes. New **last step**: end with an explicit cut (state is on disk → `/clear` → resume with `/status`) and stop, instead of rolling into the next task. Measured: 19 sessions, several past 400 hours, 8 handovers written and **zero** `/clear` — the note was being written and the session rolled on anyway. Cache makes a long window cheap, not good.
- `/status` — now flags a task count it does not believe, permanently-red gates, promotable lessons, and uncollected background agents.
- `.claude/docs/context-engineering.md` — two additions: continue a live agent instead of re-dispatching it for a second pass on the same artifact (measured: three fresh dispatches of the same spec review in 12 minutes, ~57k tokens each); and a declared `memory:` is not a used memory.

It already caught *on disk but not indexed*; it now also catches **indexed but not on disk** (a bullet in `CLAUDE.md` whose skill/agent/command/rule no longer exists — the rename case: `the-fool` became `devils-advocate` and an index would happily keep advertising the old name) and **malformed machinery** (missing `name:`/`description:`/`paths:`, a frontmatter name that does not match the filename so dispatch-by-name silently misses, a skill directory with no `SKILL.md`, and a hook without `+x` — registered, never runs, reports nothing). - **The governance guard added for cross-repo edits never ran in an adopting project.** PR #50 put that protection inside `protect-critical.sh` — blocking `.claude/settings.json`/`settings.local.json` unconditionally, and `baseline/hooks/*.sh`, `.claude/hooks/*.sh`, `baseline/rules/**`, `.claude/rules/**` when the edit is cross-repo — but `install-harness.sh` deliberately excludes `protect-critical.sh` from the portable set it registers (it knows about lockfiles and applied migrations, which belong to a repository's own settings, not to something linked over it), so in every project that adopted the harness through the installer, the governance half of that hook simply never ran. Split into two hooks with one owner each: `protect-critical.sh` keeps only the repo-owned critical-file guard (unchanged), and the governance logic moves verbatim to a new `baseline/hooks/protect-harness.sh`, which `install-harness.sh` now registers alongside `log-edit.sh` in every mode (install, `--adopt`, `--unlink`, `--status`, `--dry-run`). Proven, not just asserted: `baseline/hooks/tests/protect-critical-harness-equivalence.test.sh` fetches the pre-split hook straight from `origin/main` as an oracle and replays all 29 payloads from both split suites (`protect-critical.test.sh`, 10 cases, and the new `protect-harness.test.sh`, 19 cases — none dropped in the split) against the pair run in sequence, matching the oracle's decision on every one.

- `log-agent.sh` was undercounting subagent cost by two orders of magnitude — it summed only `input_tokens + output_tokens` from the transcript's `usage`, ignoring `cache_creation_input_tokens` and `cache_read_input_tokens`, which are where most of a subagent's real cost lives. Measured on a real dispatch: the hook logged `tokens=169` for a call that actually created 20,347 new cache tokens and read 18,592 more — the field the harness reports as "subagent tokens" was off by ~120x, and it feeds directly into `/harness-report`'s main-thread-vs-specialist token share. `tokens=` now sums input + output + cache_creation (new context actually paid for); a separate `cached=` field (emitted only when non-zero, same convention as `dur=`/`tools=`) carries `cache_read_input_tokens` — kept apart because a cache read is real but an order of magnitude cheaper, and folding it into `tokens=` would hide that distinction. `harness-report.sh` reads `cached=` and reports it under "subagent tokens" as a `of which cache reads` line.
- `log-agent.sh` attributed every `SubagentStop` in a parallel wave to the same agent — the exact case the harness is designed to produce. It picked the subagent transcript by **newest mtime** in the `subagents/` directory; with several dispatches from one message (`/orchestrate`, `/wave`), every `SubagentStop` lands in that directory close together and every one of them resolved to the single most-recently-written file, so N agents produced N log lines all bearing the last one's type, tokens and description. Proven empirically: three synthetic payloads sharing a real multi-agent session directory, one carrying the exact `agent_transcript_path` the current client sends, one carrying only `agent_id`, one carrying neither — the third is the only one that reused the newest file, the first two each resolved to their own. Resolution is now a cascade: use `agent_transcript_path` from the payload directly if it exists; else match `agent_id` to `agent-<id>.jsonl` in the `subagents/` dir by name; only if neither is present fall back to newest-by-mtime, and mark that line `approx=1` so it reads as a guess, not a measurement. `harness-report.sh` counts `approx=1` lines and prints them as `approximate attribution` in the dispatch block, shown only when the count is nonzero.
- **`log-edit.sh` was blind to any write done through `Bash`.** It was only ever registered on `PreToolUse` for `Edit|Write|MultiEdit|NotebookEdit`, so a redirect, `sed -i`, `tee`, `cp` or `mv` never produced a log line — recorded as an open item in `baseline/docs/harness-baseline.md`'s 2026-09-10 A/B, where a run whose orchestrator edited its own tracked documents through `Bash` reported **100% delegated**, an artifact of the blind spot rather than a real number. The error runs optimistic, the worse direction for something whose job is answering whether the harness is used as designed. `log-edit.sh` now also runs on `PreToolUse`/`Bash`: a small character-level lexer (not a full shell parser) tracks quote state, recognizes `>`/`>>`, `sed -i`, `tee`, `cp`, `mv`, and explicitly excludes `2>`/`&>`/`>&` (stderr/combined redirects, `2>&1` chief among them — never a new file) and `[[ ... ]]`/`(( ... ))` (a shell comparison whose literal `>` is not a redirect). A target is logged only when it resolves **inside the repo** (the hook's own cwd) — `/dev/null`, `/tmp`, the session scratchpad and anything else outside the project are dropped by that one rule instead of a growing exclude list. A target the lexer cannot resolve to a literal path (a shell variable, a command substitution) is not dropped: it is logged with `path` equal to `?`, since the thread is still known and the delegation count still needs it — only the by-extension breakdown loses that row, and it says how many it dropped rather than doing so quietly. `.claude/tool-log.txt`'s `tool` column now also carries `Bash:redirect`/`Bash:sed-i`/`Bash:tee`/`Bash:cp`/`Bash:mv` alongside the existing four; the column count and position are unchanged. `harness-report.sh` counts these writes toward delegation like any other, reports how many came from `Bash` and how many of those are unresolved on their own line (a number a reader cannot audit against the log has to announce itself), and the main-thread-by-extension breakdown now says how many rows it ignored for having an unresolved target instead of silently under-representing them. `install-harness.sh` and this repo's own `.claude/settings.json` register `log-edit.sh` on the `Bash` matcher alongside `block-secrets.sh`/`protect-main.sh`, in addition to its existing registration on Edit/Write/MultiEdit/NotebookEdit. Declared, not fixed: a write performed entirely inside a heredoc handed to another interpreter (`python - <<PY` ... `open(path, "w")` ... `PY`) has no shell-level operator for this lexer to see and is not detected at all — flagging every such heredoc as a phantom write would trade an undercount for a worse overcount. **Any delegation percentage in `harness-baseline.md` measured before 2026-09-12 is not comparable to one measured after it**: the denominator changed, so a rise or fall across that date is not yet evidence of a behaviour change. - `log-edit.sh` attributed every specialist's file edit to the main thread — the opposite direction of the two `log-agent.sh` bugs above, and the one that fed the harness's headline number. It classified the thread by inferring from `transcript_path` alone: `main` unless the path contained a `subagents` segment. Measured effect: `harness-report.sh` reported `DELEGATED 0%` for a session in which two `implementer` dispatches had actively edited files — every specialist edit landed in the main-thread bucket, systematically, in one direction only. The header comment's claim that the heuristic "records `?` rather than guessing" was false for this case: it guessed `main` with full confidence, not `?`. - `/handover` — the no-spec path added the day before wrote its git-exclude line to the literal `.git/info/exclude`, which **does not exist inside a worktree**: there `.git` is a file pointing at the real gitdir, so the append fails with `not a directory` and the handover silently stays visible to git. Found by hitting it while setting up a measurement worktree. The path is now resolved with `git rev-parse --git-path info/exclude`, which is correct in both layouts. Worth the entry because this harness puts one worktree per feature, so the broken case was the common one, not the edge.

The no-spec path is the common one for repo-level and harness work, so the failure was not an edge case. The closing cut now names the real path it wrote instead of hardcoding the spec path, since a cut that points at the conversation points at what it is about to erase.
- `protect-main.sh` resolved the branch to protect from the **hook's own cwd**, not the repository the command actually targets — two bugs, both reproduced directly. False positive: a session with cwd on repo A's `main`, running `cd /path/to/repo-B && git add -A && git commit` against repo B's unprotected feature branch, was blocked anyway because the hook read `main` off repo A. False negative, the graver one: the "is this a git command" gate only matched `^\s*git\s`, the literal start of the string, so a one-line `cd <repo-on-main> && git commit -m x` never matched at all and the commit went straight through — the guard never protected the exact case it exists for. The two compound: the hook protects the wrong repo and stops protecting the right one in the same breath. Detection now resolves a target directory before asking for the branch: an explicit `git -C <path>` on the command wins, else the last `cd <path>` seen before the first `git` invocation in command position (start of line, or after `;`/`&&`/`||`/`|`/`&`), else the hook's own cwd as before — never a silent pass-through when the heuristic can't resolve a target. `git -C <path> commit` is also recognized as the dangerous op it names, not just bare `git commit`. That first pass still had a hole: a `cd` argument built from a variable (`W=<path>` then `cd $W`, a common shape in agent-issued commands) resolved to the literal, nonexistent path `$W` and fell into the "target doesn't exist" branch, which was written for a genuinely absent literal path and silently let the command through either way. A second pass tried treating an unresolvable `cd` target (anything left containing `$`, `` ` ``, `*`, or `?` after quote-stripping) as protected unconditionally, on in-doubt-protect logic — and that overcorrected: it blocked a legitimate commit in a feature-branch worktree reached through `W=<path>` then `cd $W`, and separately blocked a test script that never ran git at all, because the pattern check matches text and the script's JSON payload happened to contain the string `cd $S/repo-main && git commit` as *data*, not a command. Two false positives in legitimate work in quick succession is a guard that gets disabled by its own users, which protects nothing. An unresolvable `cd` target now falls back to the branch of the hook's own cwd instead — the same fallback already used when there is no `cd` at all — and is judged by the normal per-branch check, not blocked outright. **Accepted gap, left in deliberately**: this means `cd $VAR && git commit` against a repo on `main`, run from a cwd on a feature branch, passes undetected; the hook cannot tell what `$VAR` resolves to without expanding command input, which is itself the class of risk this hook exists to prevent. Anyone who needs the guard to hold through a variable `cd` can make the target resolvable: write the literal path, or use `git -C <path>`. Verified with the same two synthetic repos and eleven payloads, including the variable-`cd` case (now expected to pass, not block) and its mirror (cwd on `main`, variable pointing at the unprotected repo, still correctly blocked because the check falls back to the cwd's own — protected — branch) — all eleven return the expected exit code.
- `protect-main.sh` again — two more defects, both reproduced, both from evaluating a multi-invocation command as one flat blob instead of one invocation at a time. **Unanchored patterns**: `dangerous_patterns` matched `git\s+merge` as a bare substring, so `git -C <repo-on-main> merge-base --is-ancestor A B` — a read-only ancestry query — tripped the same pattern as `git merge <sha>` and was blocked for no reason. **Single-target evaluation**: the hook resolved ONE target directory for the whole command (from the first `git` at a command position, or the last literal `cd` before it) and then matched the dangerous patterns against the ENTIRE command text. The false positive reproduces when the later dangerous invocation is reached through a `cd`: `git -C <main-repo> rev-parse HEAD` then `cd <feature-worktree>` then a bare `git push` was blocked even though the push targets the unprotected feature repo, because the old hook ignores any `cd` that appears after the first `git` line and the unqualified `push` still matches the whole-command regex against the first (protected) target. The same later invocation addressed explicitly (`git -C <feature-worktree> push`) was invisible to the old match in the first place, not caught by it: only the FIRST `git` line ever had its `-C` stripped before matching, so `git\s+push` could not match `git -C <path> push` (after `git` comes ` -C`, not `push`) — this shape passes on both the old and the new hook and is asserted only to prove the per-invocation walk keeps it passing, not as a regression guard. The false negative reproduces regardless of addressing style: a read-only first invocation against an unprotected repo made the old hook exit before the dangerous-pattern loop ever ran, so a real `git -C <checkout-on-main> push` arriving later in the same command passed uninspected either way. All six patterns are now anchored with a word boundary right after the subcommand (`git\s+merge(\s|$)`), so a suffixed subcommand like `merge-base` no longer matches while `git merge <sha>` still does. Detection is now per invocation: the hook walks the normalized lines in order, keeps a running current directory that only a literal `cd` updates, and for every line that is a `git` invocation at a command position resolves that invocation's own target (its own `-C <path>`, else the running `cd`, else the hook's own cwd), matching the dangerous patterns against that invocation's own `-C`-stripped line only — and blocks the whole command the moment ANY invocation is dangerous against a protected branch. The old whole-command `check_target` is gone. The accepted gap from the previous fix is unchanged: an unresolvable `cd` argument (`$VAR`, command substitution, a glob) still resets the running directory to the hook's own cwd rather than being expanded, for the same reason as before — expanding input taken from the command under inspection is how you create the accidental execution this hook exists to prevent. Verified with a new standalone fixture suite, `baseline/hooks/tests/protect-main.test.sh` — two throwaway git repos built in a `mktemp -d` (one on `main`, one on `feature/x`, each with two commits so `merge-base --is-ancestor` has real revisions), 20 cases covering both defects, both invocation orders, per-invocation `cd` retargeting, and the accepted gap in both directions (labeled in the test output as the documented gap, not as correct protection). Falsifiability checked both ways: run against the fixed hook, all 20 pass; run against the pre-fix hook (`git show HEAD:baseline/hooks/protect-main.sh` before this change), exactly the five cases that encode the two defects fail (the unanchored `merge-base` case, the `cd`-reached false positive, the false negative, and the two per-invocation `cd`-retargeting cases) and the other fifteen still pass — proof the suite catches the bugs it was written for, not just that it passes after the fact.
- **`log-agent.sh`'s own degree-3 fallback double-billed subagent tokens in a parallel wave, and `harness-report.sh` mixed two eras of the log into one number.** The comment above degree 3 (newest-transcript-by-mtime, for older clients that send neither `agent_transcript_path` nor `agent_id`) already named the parallel-wave collision — every `SubagentStop` in the wave resolves to the same file — but did not act on it: each collision copied that file's real metrics again, so N agents in a wave summed one transcript's tokens N times, not once. Measured on this machine's own `.claude/agent-log.txt` (135 lines): 22 `approx=1` lines, all correctly typed (the agent type comes from the payload, not the guessed file — attribution was never the bug), three of them sharing `tokens=486296`, two sharing `tokens=293605`, two sharing `tokens=115571`. Of 11,718,022 total reported subagent tokens, 4,830,845 (41%) sat in those `approx=1` lines, indistinguishable in the total from a real measurement. Fix: a small gitignored registry, `.claude/.agent-log-consumed` (one `<session><TAB><transcript path>` line per file degree 3 has already billed this session, guarded by an exclusive `fcntl.flock` held only for the short check-and-record, never across the transcript scan itself) — the first `SubagentStop` to land on a file gets its real metrics, every later hit on the same file gets `agent=` (still reliable) and `dup=1`, with no `tokens=`/`cached=`/`dur=`/`tools=` at all, rather than a copy. Separately, `harness-report.sh` read the entire `agent-log.txt` as one series; all 85 of its `agent=?` lines predate the 2026-09-09 fix documented in `harness-baseline.md` ("no report before this date is usable"), yet the script reported them as live, which is how a stale 63%-unattributed figure got relayed as current state. `harness-report.sh` now reads an `<!-- instrument-epoch: YYYY-MM-DD -->` marker out of `harness-baseline.md` (taking the latest one it finds, so a future fix only has to add a marker there, not edit the script) and excludes every line timestamped before it from all headline dispatch numbers, reporting the excluded count and the reason on its own line instead of silently dropping or silently including it. It also now excludes every `approx=1` line's tokens from the headline "subagent tokens" total — a `dup=1` line already contributes 0, having no `tokens=` field — and reports the approximate share (count and tokens) on its own line. `baseline/docs/harness-baseline.md` records the finding in a new dated section: every "subagent tokens" figure in the file up to today mixed reliable and (sometimes doubled) approximate metric with no way to separate them after the fact, so a total measured after this fix is not comparable to one measured before it, the same way the 2026-09-12 delegation entry already says about the Bash-write denominator change. Covered by `baseline/hooks/tests/log-agent.test.sh` (new) and a synthetic-log probe of `harness-report.sh`'s epoch/approx handling.
- **`check-index.sh --strict` could not pass on a repo mid-adoption, and reported a nested doc as stale.** Both surfaced adopting the harness on njord-back (`njord-app/njord-back#885`), following `ADOPTING.md` to the letter. First, the dangling-pointer scan walked `.claude/` with `find -L` and entered `*.pre-harness/` directories (`skills.pre-harness/`, `agents.pre-harness/`, the pre-migration copy `install-harness.sh --adopt` deliberately leaves on disk until the migration PR merges) and gitignored files (a 16-pointer offender in a real repo: the generated `.claude/context/repomix-snapshot.md`), reporting their old, unmaintained cross-references as real drift. `--strict` could only reach 0 by moving those directories aside, which the adopting guide also requires be kept in place, so the two requirements contradicted each other. Fixed: any path with a component ending in `.pre-harness` is skipped unconditionally, and any file git considers ignored is skipped when git is available; `find -L` still follows symlinks, since that is how a consumer's own `.claude/skills`/`.claude/docs/harness` links resolve at all. When git is unavailable (no `git` on `PATH`, or the tree is not a git repository), the scan skips nothing rather than guessing: an unverifiable "probably ignored" could hide a real dangling pointer, the exact failure class this script exists to catch. Second, a doc listed in `CLAUDE.md` that lives under a subdirectory (`context-engineering.md`, `dispatching.md`, `superpowers.md`, all real, all under `.claude/docs/harness/` via the harness link) was reported as "listed but not on disk", because the docs check built its known-names list from a flat, non-recursive `docs/*.md` glob while the rules check next to it already walks recursively for the identical reason. The docs check now walks `docs/` recursively too, the same mechanism, not a second one. Covered by new `baseline/scripts/tests/check-index.test.sh`: pre-harness and gitignored broken pointers are not reported, a broken pointer in a tracked file still is (positive control), a nested doc that exists is not stale, a doc that exists nowhere still is, `--strict` exits 1 with the positive control and 0 without it, and a no-git fixture proves the fail-open fallback surfaces rather than hides an unverifiable pointer. Verified against `origin/main`'s copy of the script: 7 of 12 assertions fail there and all 12 pass here.

- **`install-harness.sh --adopt` printed the "tracked files were deleted" NOTE even when nothing tracked was set aside.** Reproduced against a real njord-back checkout that had `git switch`ed onto a `develop` which had already dropped the vendored `.claude/skills`/`.claude/agents` copy from version control: git removed the tracked files but left the directory on disk because a single ignored file, macOS's `.DS_Store`, still sat inside it, and git does not remove a directory that still has content. `--adopt` correctly buried that leftover directory as `.claude/skills.pre-harness` and `git ls-files --deleted` reported nothing, yet the closing message still warned "the files you set aside are tracked, so git now reports them as deleted. Do not commit while adopted", telling someone who did nothing wrong to undo a correct adoption. `install-harness.sh` now checks, with a new `has_tracked()` helper run against git before each directory or per-file collision is buried, whether anything git actually tracks is inside it; the scary NOTE only prints when that check finds a tracked file (proven with a control case: a repo whose `.claude/skills` holds a committed file still gets the NOTE, unchanged). When the only thing set aside was untracked or ignored content, a short reassuring line prints instead, saying the `.pre-harness` copy can be deleted whenever, with nothing to restore. Adoption behavior itself is unchanged.
