## [Unreleased]

### Added

**Delegation and dispatch discipline** — from telemetry on a real project running this template (22 sessions, 54 subagent dispatches):
- `.claude/rules/delegation.md` (always loaded) — the main thread coordinates, specialists implement. The rule previously existed only inside `/orchestrate`, a command that ran twice in 729 prompts; meanwhile 71% of `Edit` calls happened in the main thread while `Grep`/`Glob` were 100% delegated. Also added to `AGENTS.md` non-negotiables.
- `.claude/docs/dispatching.md` — opens with the **six topology shapes** (pipeline, fan-out/fan-in, expert pool, producer-reviewer, supervisor, hierarchical delegation): what each fits, what to watch for, and how to run each with sub-agents, since picking the wrong shape costs more than any mechanic recovers. Catalogue adapted from [revfactory/harness](https://github.com/revfactory/harness) (Apache-2.0). Then the mechanics: parallel means several agent calls **in one message** (measured: 54 of 54 dispatches went out one per message, so the wave plan never actually fanned out); background only for long work collected in the same turn (measured: two dispatches collected 16 days after launch, across a suspended session); never background a gate; concurrency ceiling; diversity over redundancy; agent memory.
- `.claude/rules/specs.md` (`paths: specs/**`) — claims about the current state of the system are verified against code/git when written, never copied from existing prose; a hand-written spec still goes through `spec-reviewer`. Includes the cheapest check for a referenced "pending fix": a `git cherry-pick` that comes back **empty** means the content is already in your base, re-applied under a different PR number. Measured: a follow-ups spec was written from a three-week-old header claiming two tests were failing; they had been fixed and merged under another PR, and the block was ranked priority 1. The defense already existed (`write-spec` hands the spec to `spec-reviewer` to verify claims against the codebase) and was skipped because the spec was written by hand — a guard that only fires on the happy path is not a guard.
- `/wave` command — the low-ceremony half of `/orchestrate`: one batch of independent tasks, dispatched in parallel, gated once, then stop. No spec, no approval table, no PR.
- **`deviations.md`** — a fifth spec-folder artifact, created on demand, for where execution left the agreed plan: assumptions taken, blockers worked around, scope changed mid-flight, phases run straight from `plan.md` instead of as tasks. Distinct from `lessons.md`, which is about the system (*this broke, here is the fix*, promotable to a rule) where a deviation is about this feature's plan (*we agreed X and did Y*, resolved and closed, never promoted). Format and the four things that belong in it are in `.claude/rules/specs.md`; `/orchestrate` and `/wave` append as they go, `/status` lists open entries, `/handover` lifts every `needs decision` into open decisions. Measured: deviations with nowhere to go get narrated inside `tasks.md`, where prose competes with the checkboxes and the next wave plan ignores it — which is how a task file becomes a state dump. Concept adapted from [migoVanDingo/base-template](https://github.com/migoVanDingo/base-template).

**The harness measures itself** — `log-edit.sh`, `harness-report.sh`, `/harness-report`, `.claude/docs/harness-baseline.md`:
- `.claude/hooks/log-edit.sh` (PreToolUse on Edit/Write/MultiEdit/NotebookEdit) appends one line per file edit recording **which thread** made it, main or specialist, to the gitignored `.claude/tool-log.txt`. Thread detection is a heuristic on the payload (a subagent's transcript lives under `subagents/`); when it cannot tell it records `?` and the report counts unknowns separately rather than folding them into either side.
- `/harness-report` and `.claude/scripts/harness-report.sh` turn the two observability logs into the delegation ratio, the dispatch mix, and the unattributed count.
- `.claude/docs/harness-baseline.md` records what was actually measured before the corrections (Edit delegated **29%**, main thread carrying **71%** of tokens, **1.0** dispatches per message, `/orchestrate` run twice in 729 prompts) and states, per correction, which number would confirm it — including the honest possibility that delegation does not move, in which case prose is the wrong mechanism and a sentence will not fix it.

Why this exists: `rules/delegation.md` was written to fix inverted delegation, and the 29% was measured with that rule already in place inside `/orchestrate`. A rule nobody can see being broken decays silently. Making it countable is what gives it teeth — and what lets the four corrections shipped in this release be judged rather than assumed.
**Two quiet failures of the link model, closed:**
- `check-baseline.sh` now warns on a **broken link**. This is the model's worst failure and its quietest: move the harness checkout and every link in every project that opted in resolves to nothing — and Claude Code does not error on that. The skills, agents and rules are simply absent, so a session looks completely normal while running unarmed. The check runs before the staleness report, because a dead link makes that report moot, and it says out loud that silence is the symptom.
- `spec-worktree.sh` now carries the harness links into a new worktree. They are excluded from git, so they exist only in the worktree that created them — a new worktree of a repo that opted in would otherwise start **without** the harness, silently, the same failure by a different route. It points at whatever target the main checkout uses rather than re-deriving it. Verified: a fresh worktree resolves all three links and reports 19 skills.

**`install.sh` now sets up a project's context, not the harness** — the split ADR 0003 implies, made real:
- Two commands, two jobs. `./install.sh --to <repo>` delivers what a repository **owns and commits**: `AGENTS.md`, `CLAUDE.md`, `docs/`, `specs/`, `.claude/settings.json`. `./install-harness.sh` delivers the machinery, by symlink, never committed. Before this, `install.sh` copied `.claude/` wholesale because the machinery lived there — it does not any more, so that copy would have delivered almost nothing while implying it had delivered a harness.
- **It also ships the repo-owned guards.** `protect-critical.sh` (lockfiles, applied migrations, generated code) and `check-snapshot-on-session.sh` are guards, not method: they must hold for a teammate who never installed the harness, so they are copied and committed rather than linked — which is precisely why `install-harness.sh` refuses to register them. `check-snapshot.sh` rides along, since the hook calls it.
- The copied `settings.json` is rewritten to reference `.claude/hooks/…` and to list **only** those two. The portable hooks arrive in the gitignored `settings.local.json` when someone links the harness. Without this rewrite a fresh project inherited hook paths pointing at `baseline/`, which exists only in the harness checkout — every hook would have failed silently.

**The harness is linked into the projects you choose** — `baseline/` + `install-harness.sh`:
- The machinery moved from `.claude/` to **`baseline/`** at the repo root. `install-harness.sh`, run from inside a project, symlinks `baseline/{skills,agents}` into that project's `.claude/` and `baseline/rules` into `.claude/rules/harness/`. **Opt-in per repo** — you run it where you want it and nowhere else. `--global` still exists for machine-wide, `--unlink` takes it back out, and `--status` says what is linked.
- **Nothing is committed.** The links go into `.git/info/exclude`, which is per-clone and never leaves the machine, and hooks are merged into the already-gitignored `.claude/settings.local.json` rather than the repo's `settings.json`. A teammate cloning the repo sees no dangling symlink and CI sees nothing at all — so linking a repo you share with other people is safe.
- **Works in a worktree.** The exclude path is resolved with `git rev-parse --git-path` instead of assuming `.git` is a directory — in a worktree it is a *file*, so the old test reported "not a git repo" and silently skipped excluding the links. `info/exclude` lives in the common git dir and is therefore shared by every worktree of the repo; that is harmless (the paths it lists are tracked in the others, and gitignore does not affect tracked files) and the installer says so rather than leaving it as a surprise.
- **Absolute paths**, so there is no sibling-clone assumption: a work repo, a new site and a throwaway experiment all work the same.
- **Rules land in a subdirectory** (`.claude/rules/harness/`) instead of replacing the folder. Rules are discovered recursively, so a repo's own rules keep working alongside — and a project rule still wins over a harness one.
- Updating every project that opted in is `git pull` in the checkout, which retires the `install.sh --update` idea entirely.
- **The six commands are now skills.** A `commands/deploy.md` and a `skills/deploy/SKILL.md` produce the same `/deploy`, so authoring them as skills means nothing depends on a personal `commands/` path that was never verified.
- Every `.pre-harness` file is excluded from git, at any depth — the first pattern missed `.claude/commands/*.pre-harness`, leaving five untracked files in `git status` during an adoption, one `git add -A` away from being committed.
- The installer refuses to clobber: if `.claude/skills` exists and is not its link, it stops and changes nothing rather than deleting what you wrote. **`--adopt`** is the way through for a repo that already has a copied harness: it renames what is in the way to `.claude/<name>.pre-harness` and links over it, and `--unlink` puts it back. It also handles the collisions a directory link cannot — rules and commands **merge** rather than being replaced, so a repo that copied the harness would otherwise load `delegation.md` twice (its own beside the linked one) and keep a stale `commands/orchestrate.md` shadowed by the linked skill; those individual files are set aside too. Measured on a worktree of a real repo: 2 directories and 10 files, all restored by `--unlink` — so the new model can be tried on a real repository and fully reverted with one command. While adopted, git reports the set-aside files as deleted (they are tracked, and the symlink does not expose them); the installer says so and tells you not to commit, **merge or pull** in that state. The merge half is the one that bites: git writes those files back over the links, leaving a real directory beside an orphaned `.pre-harness` that `--unlink` cannot repair because the destination is occupied. Found by merging into an adopted worktree and watching it happen. `protect-critical.sh` and `check-snapshot-on-session.sh` are deliberately left out of what it registers — one knows about lockfiles and applied migrations, the other about a per-repo snapshot, so both belong to a repository's own settings.
- `check-index.sh` now scans `baseline/` and `.claude/` for what a repo owns, and `~/.claude/` for **names only** — without that split, a project that linked the harness would report `/orchestrate` as *indexed but not on disk*.
- `check-baseline.sh` was rewritten for the model it lives in: it reports whether **your checkout** is behind its remote or carries **uncommitted** edits under `baseline/` — which are live in every project that linked it, unreviewed. It does not fetch, so "up to date" means "as of your last fetch", and it says so.

Rationale and the accepted costs: ADR 0002/0003 in the njord marketplace.

**The harness repo can use its own harness again** — a regression from the `baseline/` restructure:
- Moving skills, agents and rules to `baseline/` never linked them back into `.claude/`. Claude Code discovers machinery under `.claude/`, never under `baseline/`, so a fresh session opened in this repository had **no `/orchestrate`, no agents and no rules**. The harness could not use itself.
- Fixed with **committed relative symlinks**, not by running the installer here. Inside its own repository the target is always in the tree, so a relative link is correct in every clone with no install step, and it survives the checkout being moved — which the absolute links the installer writes for consumers do not. Verified on a fresh clone: 19 skills, 7 agents and 5 rules resolve with nothing run, and they still resolve after the clone is moved to a different path.
- `check-index.sh` was reporting every finding **twice**, since `.claude/skills` and `baseline/skills` became the same directory reached by two paths. It now resolves each candidate root with `pwd -P` and keeps only the ones that are new, which also covers a consumer repo whose `.claude/skills` points outside the repo.
- The installer's guard for being pointed at the harness itself said *"it already has baseline/"* — the wrong reason, since having `baseline/` is not the same as being able to use it. It now explains the committed relative links and exits 0, because there is nothing to do rather than something wrong.
**Waves are sliced by cohesion, not by task** — `/orchestrate`, `/wave`, `dispatching.md`:
- Step 1 now groups the unchecked tasks into **a few cohesive clusters of 5-7 tasks**, one specialist per cluster running them **in order in its own context**, instead of one dispatch per task. Clusters must touch disjoint files (they go out together); tasks *inside* a cluster may share files freely, which is what allows a cluster to be cohesive at all.
- The reason is not speed. On an 18-task epic, one-agent-per-task measured **25M tokens / 43m / 0.81** against **10.5M / 18m / 0.95** for ~3 clusters — worse than not dispatching at all. Three findings are now written down, and only the first is intuitive: granularity destroys quality (every dispatch starts from zero and loses the whole); **more workers can leave the main thread fatter**, because each summary returns to it (18 workers used more of it than 7); and the actual win is finishing at **26% of the window instead of 74%**, so the correction rounds are cheap rather than degrading. Eighteen minutes against nineteen is no speed-up.
- Consequently a cluster is told to report **once, not once per task** — a per-task report undoes the context saving that clustering bought.
- `dispatching.md` gains the question that came before its six topology shapes: **whether to dispatch at all** (always for codebase sweeps and research; clustered for long runs; inline for small cohesive work; parallel only when files are genuinely disjoint).
- Numbers from a [Tech Leads Club](https://agent-skills.techleads.club/tlc-spec-driven/) benchmark, and recorded in `harness-baseline.md` under a new **imported hypotheses** section rather than mixed in with our own measurements. n=1 per architecture, and its authors call the 0.93 vs 0.95 gap statistically indistinguishable — so the **shape** is adopted and the **number** is flagged as unverified here. Size by tasks per specialist (5-7), not by a fixed count of three.
- Worth stating plainly: our own telemetry sits at the *opposite* failure — 1.0 dispatches per message, 29% of `Edit` delegated — while `/orchestrate` as written would have produced the worst row. Both errors point the same way, which is why the shape is adopted before we have measured it ourselves.

**`check-index.sh` stops crying wolf in a repo that linked the harness** — found by running it in a real one:
- **Rules are discovered recursively** by Claude Code, and the harness lands its own under `.claude/rules/harness/`. A flat glob reported all five as *indexed but not on disk*. It now walks the tree — with `find -L`, since that subdirectory is a symlink and `find` does not follow one by default.
- **Machinery a plugin provides** lives in `~/.claude/plugins/marketplaces/`, which no `.claude/` scan can see. Every repo enabling a stack plugin reported its agents and skills as missing — 12 false entries in `njord-back` alone. Plugin names now count as existing.
- Verified on a worktree of `njord-back`: 17 reported entries dropped to **1**, and that one is real — `CLAUDE.md` there still lists `the-fool`, renamed to `devils-advocate` two days ago. The reverse check caught genuine drift in a production repo, which is what it was built for.

**The installer falls back to copying when the platform will not symlink** — Windows is not hypothetical, a teammate uses it:
- Git Bash on Windows silently refuses to create a symlink without Developer Mode, and a "symlink" that is quietly a copy is **worse than an honest copy**, because every promise this installer makes about `git pull` updating it would be false. It now creates the link, **verifies it actually became one**, and on failure copies instead, marks the copy with a `.harness-copy` file, and says so in capitals.
- `--status` reports `COPIED` for those entries and tells you to re-run after pulling; `--unlink` removes a copy it made, which it can only do safely because of the marker — without it an interrupted install is indistinguishable from a folder the repo owns.
- Verified both paths: the normal symlink install is unchanged, and with `ln` forced to fail the three entries copy, report, are recognised by `--status`, and are removed cleanly by `--unlink`.

**The three guard hooks never blocked anything on macOS** — found while adding a fourth:
- All of them extracted the command with `grep -oP`, which is **GNU-only**. On macOS BSD grep that is `invalid option -- P`, the extraction returned empty, and every guard exited 0. `block-secrets.sh`, `protect-main.sh` and `protect-critical.sh` have been decorative since they were written. Extraction now goes through `python3`, which the other hooks already depend on.
- And they blocked with **exit 1**, which is a *non-blocking* error in a `PreToolUse` hook — the tool call proceeds. Blocking is **exit 2**. So even with the grep fixed they would still have let everything through. Both bugs had to be present for the failure to be this quiet.
- Verified after the fix: committing on `main` blocks, editing `yarn.lock` blocks, reading `.env` blocks, and an ordinary `gh pr merge` and an edit to `src/app.ts` pass.

**`gh pr merge --admin` is now blocked outright** — on any branch, in any repo:
- The flag bypasses branch protection, which removes precisely the review that catches an unreviewed commit riding into a PR under another change's title. That is not hypothetical: it happened in this session, and the cost was paid by the repository rather than by whoever ran the command.
- `.claude/rules/git-workflow.md` gains the three rules the incident produced: **branch from the remote ref** (`git checkout -b x origin/main`, never from a local branch that may carry unpushed commits), **read `gh pr view --json files` before merging a PR a script opened**, and **never `--admin` on a shared repo**. The rule states why it is a rule after one occurrence rather than the usual three: the cost lands on someone else and is invisible once merged.
- The guards proved themselves three times over, each by blocking something they should not have. The merge guard blocked the command used to test it (correct), then the commit that introduced it, because the flag's name appeared in the PR body. The secrets guard then blocked a PR body containing `.env` next to a markdown table pipe. All three patterns are now anchored at a **command position** (start of a line, or after `;` `&&` `||` `|`), so writing about a command is not the same as running it — an unanchored guard that has just come back to life fires constantly on documentation.
- The secrets patterns also gained a real bug fix while being rewritten: `echo $API_TOKEN` never matched, because `$[` inside a double-quoted bash string is parsed as deprecated arithmetic expansion and ate the pattern. Verified on seven cases: four reads block, and a markdown table, a commit message and `.env.example` pass.
- The merge guard proved itself immediately by blocking the command used to test it — and then blocked the commit that introduced it, because the flag's name appeared inside the PR body. It now matches only at a **command position** (start of a line, or after `;` `&&` `||` `|`), so documenting the command is not the same as running it. Verified on four cases: a direct call and a chained one block; the same words inside a commit message, and an ordinary `gh pr merge`, pass.

**A fallback copy that goes stale is now detected** — the half of the Windows story that was missing:
- `check-baseline.sh` compares a copied entry against the harness it came from and warns when they diverge, so a person on copy mode is told to re-run the installer instead of silently running an old harness. Nothing else would have told them: `git pull` updates the checkout, not their copies.
- It also stopped lying. The uncommitted-edits warning claimed those edits were **live in every project on this machine**, which is false for anyone on copy mode — their copies are frozen. It now says *every project that linked* the harness, and states that copies are unaffected until the installer is re-run there.
- Verified: a copy matching the harness reports nothing; after one line changes in the harness, the copy is named and the fix is spelled out.

**The top-level documentation described a layout that no longer exists:**
- `README.md` carried **13** references to the pre-restructure paths, **zero** mentions of `baseline/` or either installer, and a project tree listing 11 agents (there are 7), an `example-skill` that was deleted, and **12 of the 19 skills missing** — including `orchestrate`, `wave`, `handover` and `verify-before-done`. `LEARN.md`, `CONTRIBUTING.md` and `AGENTS.md` were stale the same way, including two `find` commands in `AGENTS.md` that would return nothing.
- This was not cosmetic: `ADOPTING.md` points a new adopter at the README for the structure, so they would read the right guide and land on the wrong map.
- The tree now shows `baseline/` and `.claude/` as **two directories with two jobs**, and the README gains the piece it never had: **what the two installers are and why there are two** — context is copied and committed, method is symlinked and never committed.
- Worth noting the gate did not catch any of this. `check-index.sh` validates `CLAUDE.md` only, so drift in the human-facing docs is invisible to it.

**`implementer` — the baseline finally ships something that writes code:**
- The baseline had seven agents and not one of them implemented a feature. Implementers were left to stack plugins, which is right in principle (a NestJS agent is useless in a Next.js repo) and wrong in practice: `delegation.md` says *never write feature code in the main thread, dispatch it*, while the baseline shipped **nobody to dispatch to**. Two of the four njord repos have no stack specialist at all, and neither does any new project.
- The fallback until now was Claude Code's built-in `general-purpose` agent, measured on real telemetry as **the most expensive agent in the estate — a median of 122 tool calls per task** — because it starts knowing nothing and rediscovers the repo every single dispatch.
- `implementer` is portable the way `tester` already is: it learns the stack from `AGENTS.md`, the conventions from `.claude/rules/` (including a linked harness's), and the shape from the code next to the change. It is explicitly the **fallback** — if a stack specialist exists it says which one and stops — and it **names the missing specialist in its report**, so the gap lands in the plugin instead of being paid for silently on every future task.
- `delegation.md`, `/orchestrate` and `/wave` now point at it instead of at `general-purpose`.

**`jury` — a skill that decides between options:**
- `grilling` builds a decision with a human and `devils-advocate` attacks one already made. Neither **chooses between alternatives**, which is the shape of most expensive calls — and of at least four made in this repo's own history, two of which were reversed within hours.
- Three to five subagents argue **blind in round one** (dispatched in a single message, so context isolation makes anti-anchoring structural rather than a rule to trust), then deliberate on **anonymised** positions, steelmanning before rebutting. A change of mind must cite the argument that caused it; an uncited flip is flagged as bandwagon and the verdict falls back to the blind round at LOW confidence.
- Hard cap of five, because beyond that a panel adds **correlated noise, not signal** — the same effect the dispatch-granularity study found from the other direction.
- Evidence is graded A-D and caps confidence; **there is no abstention**, since refusing to decide is the foreman failing at the only job the panel was convened for. A verdict that changes how the system is built becomes an ADR, carrying its **dissent** and **riskiest assumption** — an ADR that records only the winning argument cannot be re-evaluated later.
- Adapted from `the-jury` by Tech Leads Club (CC-BY-4.0). Their `the-fool` was compared against our `devils-advocate` in the same pass and needed **no changes**: steelman, mode selection, bias scan, 3-5 challenges, engage-before-synthesise and the HIGH/MEDIUM/LOW/PIVOT verdict were all already there.

**`README.md` cut from 616 lines to 170:**
- Four reference sections and a guide moved to `docs/reference/` and `docs/guides/` rather than being deleted — layers, the spec-driven model, the where-does-it-go decision table, the ecosystem, and brownfield adoption. Registered in `docs/README.md`.
- Five sections of meta-commentary (who it is for, how to read it, why it exists, what it demonstrates) collapsed into one **Start here** table and a five-line statement of what the harness bets on.
- The 75-line project tree became a 20-line one that names the directories and their jobs, and points at `CLAUDE.md` for the per-item list — which is the file `check-index.sh` actually validates, so it cannot silently drift the way the tree did.

### Changed

- `/orchestrate` — **Step 3 now executes one wave at a time instead of one task at a time.** The loop was written `for each task: dispatch → gate → review → tick → next`, which is a queue wearing a wave's name: it plans a fan-out in Step 1 and then serializes it in Step 3, paying full latency per task and delivering nothing the plan promised. Measured: 54 of 54 dispatches went out one per message, so no wave plan ever actually fanned out — and the old wording (*"may be dispatched in parallel (background)"*) both permitted the serial path and pointed at background, the mechanism that left two dispatches uncollected for 16 days. Now the whole wave goes out in **one message**, is collected as a barrier, and is gated **once in the foreground**, with the reviewers the wave's classes selected also dispatched together. Gating a batch costs attribution, so a red gate now requires attributing the failure against the files each specialist reported touching — and gating the suspect task alone rather than guessing when that is ambiguous. Waves must contain tasks that touch **disjoint files** (Step 1), which is what makes single-message dispatch safe. Invariant updated: boxes are ticked only on a fresh green gate covering that wave, and a task whose specialist came back short does not inherit a box from its wave-mates.
- `/orchestrate` — new **Step 0 (reconcile)** and a **class-to-gates matrix** in Step 1. Step 0 audits the unchecked tasks against the code and `git log` before any planning, reports the drift in both directions (unchecked-but-done, checked-but-absent) and halts to fix the file: measured, a shipped feature's `tasks.md` sat at 78 open / 12 done and had been copied into three worktrees, so a wave plan would have dispatched a specialist per finished task. Step 1 now classifies each task (schema, logic, API, UI, tests, chore, docs) and selects only the gates that class needs, instead of running `tester` + `code-reviewer` + docs on everything — that uniform ceremony is why the command ran twice in 729 prompts. The build gate never gets skipped, the stricter row wins on ambiguity, and a task whose diff outgrew its class is re-classified before the box is checked. Phase-0 audit and the phase-selection matrix adapted from [revfactory/harness](https://github.com/revfactory/harness) (Apache-2.0).
- `/handover` — now built on **state, not instructions**: it describes what *is true*, never what the next agent *should do*. The `Next steps — the concrete next 1-3 actions` section is gone, replaced by `Current state` and `Not started`; the single forward-looking sentence lives in the closing cut, where it is cheap to discard when wrong. An instruction written now ages worse than a fact — *"implement logout next"* is wrong the moment priorities change, while *"logout is not started"* stays true until someone touches it. Three independent sources converged on this (`davidondrej/skills`, the `_features/` rule in `migoVanDingo/base-template`, and this command's own Step 0), and the command was violating it while teaching it. Also added: **reference, don't duplicate** (stronger than the old "don't paste diffs" — it also rules out restating an ADR's reasoning or a spec's requirements, which creates a second copy that drifts), **frame claims as claims** (mark anything not verified this session as unverified; `.claude/rules/specs.md` applies to a handover too), and the handover is now **printed as a single fenced block** in chat as well as written to the file, since the block is what actually gets carried across the cut. The closing cut template was in Portuguese in an otherwise English template; it is now English. Principles adapted from [davidondrej/skills](https://github.com/davidondrej/skills).
- `/handover` — new **Step 0**: reconcile `tasks.md` against reality before writing the narrative, and check `lessons.md` for a class of failure worth promoting to a rule. Prose and checkboxes are two states of the same file and only one is machine-readable; a handover written over stale boxes documents a fiction that the next wave plan then executes. New **last step**: end with an explicit cut (state is on disk → `/clear` → resume with `/status`) and stop, instead of rolling into the next task. Measured: 19 sessions, several past 400 hours, 8 handovers written and **zero** `/clear` — the note was being written and the session rolled on anyway. Cache makes a long window cheap, not good.
- `/status` — now flags a task count it does not believe, permanently-red gates, promotable lessons, and uncollected background agents.
- `.claude/docs/context-engineering.md` — two additions: continue a live agent instead of re-dispatching it for a second pass on the same artifact (measured: three fresh dispatches of the same spec review in 12 minutes, ~57k tokens each); and a declared `memory:` is not a used memory.
- `.claude/scripts/check-index.sh` — extended from one class of drift to three. It already caught *on disk but not indexed*; it now also catches **indexed but not on disk** (a bullet in `CLAUDE.md` whose skill/agent/command/rule no longer exists — the rename case: `the-fool` became `devils-advocate` and an index would happily keep advertising the old name) and **malformed machinery** (missing `name:`/`description:`/`paths:`, a frontmatter name that does not match the filename so dispatch-by-name silently misses, a skill directory with no `SKILL.md`, and a hook without `+x` — registered, never runs, reports nothing). New `--strict` flag exits 1 for CI; the default stays exit 0 so `SessionStart` is unaffected. Verified against fixtures for all three classes, including that uppercase (`PreToolUse`) and path-shaped (`libs/`) bullets do not produce false positives.
- `.claude/hooks/log-agent.sh` — now logs agent type, description, tokens, duration and tool count by falling back to the subagent's own transcript. The `SubagentStop` payload omitted the agent type in 183 of 238 real events (77%), which made the log countable but not attributable.

### Fixed

- `log-agent.sh` was undercounting subagent cost by two orders of magnitude — it summed only `input_tokens + output_tokens` from the transcript's `usage`, ignoring `cache_creation_input_tokens` and `cache_read_input_tokens`, which are where most of a subagent's real cost lives. Measured on a real dispatch: the hook logged `tokens=169` for a call that actually created 20,347 new cache tokens and read 18,592 more — the field the harness reports as "subagent tokens" was off by ~120x, and it feeds directly into `/harness-report`'s main-thread-vs-specialist token share. `tokens=` now sums input + output + cache_creation (new context actually paid for); a separate `cached=` field (emitted only when non-zero, same convention as `dur=`/`tools=`) carries `cache_read_input_tokens` — kept apart because a cache read is real but an order of magnitude cheaper, and folding it into `tokens=` would hide that distinction. `harness-report.sh` reads `cached=` and reports it under "subagent tokens" as a `of which cache reads` line.
- `log-agent.sh` attributed every `SubagentStop` in a parallel wave to the same agent — the exact case the harness is designed to produce. It picked the subagent transcript by **newest mtime** in the `subagents/` directory; with several dispatches from one message (`/orchestrate`, `/wave`), every `SubagentStop` lands in that directory close together and every one of them resolved to the single most-recently-written file, so N agents produced N log lines all bearing the last one's type, tokens and description. Proven empirically: three synthetic payloads sharing a real multi-agent session directory, one carrying the exact `agent_transcript_path` the current client sends, one carrying only `agent_id`, one carrying neither — the third is the only one that reused the newest file, the first two each resolved to their own. Resolution is now a cascade: use `agent_transcript_path` from the payload directly if it exists; else match `agent_id` to `agent-<id>.jsonl` in the `subagents/` dir by name; only if neither is present fall back to newest-by-mtime, and mark that line `approx=1` so it reads as a guess, not a measurement. `harness-report.sh` counts `approx=1` lines and prints them as `approximate attribution` in the dispatch block, shown only when the count is nonzero.
- `log-edit.sh` attributed every specialist's file edit to the main thread — the opposite direction of the two `log-agent.sh` bugs above, and the one that fed the harness's headline number. It classified the thread by inferring from `transcript_path` alone: `main` unless the path contained a `subagents` segment. Captured on a real `PreToolUse` payload from inside an `implementer` subagent calling `Write`: `transcript_path` pointed at the **main session's own transcript** (no `subagents` segment anywhere in it) while `agent_id` and `agent_type` were both present in the same payload — the heuristic read that as `main`. Measured effect: `harness-report.sh` reported `DELEGATED 0%` for a session in which two `implementer` dispatches had actively edited files — every specialist edit landed in the main-thread bucket, systematically, in one direction only. The header comment's claim that the heuristic "records `?` rather than guessing" was false for this case: it guessed `main` with full confidence, not `?`. Detection is now a cascade over the payload itself: `agent_id`/`agent_type` present → `sub`; else `transcript_path` contains a `subagents` segment → `sub` (kept as a fallback for older clients); else, if `transcript_path` exists at all → `main`; only absence of both → `?`. `.claude/tool-log.txt` gains a fifth column, the `agent_type` (empty when thread is not `sub`), and `harness-report.sh` reads it into a new `specialist edits by agent` line in the delegation block, shown only when non-empty. Any delegation percentage reported by this project before this fix understates delegation — the true main-thread share is smaller than what was measured.
- `/handover` — the no-spec path added the day before wrote its git-exclude line to the literal `.git/info/exclude`, which **does not exist inside a worktree**: there `.git` is a file pointing at the real gitdir, so the append fails with `not a directory` and the handover silently stays visible to git. Found by hitting it while setting up a measurement worktree. The path is now resolved with `git rev-parse --git-path info/exclude`, which is correct in both layouts. Worth the entry because this harness puts one worktree per feature, so the broken case was the common one, not the edge.
- `/handover` — **the skill told you to externalize state to the one place its own last step erases.** "Where to put it" only wrote a file when a spec was active; with no active spec it said *output it in chat*, and the very next step is the cut (`/clear`), which discards the session and the block with it. The no-spec path is the common one for repo-level and harness work, so the failure was not an edge case. Now a file is always written: `specs/<slug>/tasks.md § Handover` when a spec is active, `.claude/handovers/<YYYY-MM-DD>-<slug>.md` otherwise — kept out of git through `.git/info/exclude` rather than `.gitignore`, because a handover is local session state and the harness must not append to a committed file in a project that merely adopted it. The closing cut now names the real path it wrote instead of hardcoding the spec path, since a cut that points at the conversation points at what it is about to erase.
