# Nome do projeto (Claude Code)

> **Leia [`AGENTS.md`](./AGENTS.md) primeiro.** É a fonte de verdade para o contexto do projeto (stack técnica, comandos, estrutura, convenções, workflow e inegociáveis). O conteúdo abaixo é só o que é específico do Claude Code e não se aplicaria a outros agents.

## Específico do Claude Code: o que este projeto entrega

### `script/setup` e `script/test`, se este repo os tiver

Opcionais, e não entregues pelo harness — o time os escreve, uma vez, na raiz
do repo. Quando existem e são executáveis, `spec-worktree` roda
`script/setup` depois de criar um worktree, e `verify-before-done` roda
`script/test` como o gate em vez de redescobrir comandos. Um repo sem nenhum
dos dois não perde nada: o passo é um no-op. Veja
[`docs/guides/script-setup-and-test.md`](./docs/guides/script-setup-and-test.md).

### Skills disponíveis

As skills em `baseline/skills/` são workflows que o Claude Code auto-invoca com base nas descrições delas. Linkadas num projeto com `./install-harness.sh` (opt-in, por repo), elas caem em `.claude/skills/` daquele projeto, um link por skill, ao lado de qualquer skill que o projeto versiona por conta própria:

- `analyze-codebase` - setup único ao adotar o template num projeto existente; gera o repo map junto com os outros docs do baseline
- `refresh-snapshot` - gera manualmente um export do Repomix para entregar a uma ferramenta sem acesso ao filesystem; não é contexto, não é auto-gerado, não é auto-lido (veja `docs/decisions/0003-repo-map-over-snapshot.md`)
- `explore` - investigação livre antes de escrever uma spec
- `grilling` - entrevista implacável de uma pergunta por vez que percorre uma árvore de decisão para travar decisões abertas; chamada por `explore` para dar rigor à decisão (MIT, adaptada de [mattpocock/skills](https://github.com/mattpocock/skills))
- `find-existing-first` - reusar antes de criar, invocada antes de qualquer arquivo novo
- `write-spec` - persiste uma ideia já moldada como `specs/YYYY-MM-DD-<slug>/`, com `spec.md` preenchido e `plan.md`/`tasks.md` esqueletados
- `spec-worktree` - um worktree do git por feature (`../<repo>.<slug>`, branch a partir da branch padrão do remoto); encapsula `.claude/scripts/harness/spec-worktree.sh`
- `verify-before-done` - roda a verificação própria do repo (install, codegen, typecheck, build, tests), confirma que está tudo verde, depois escreve um relatório de evidência em `.claude/verification/` (comandos rodados, afirmações com evidência) e o confere com `verify-gate.py` antes de declarar terminado; o gate para loops automatizados (agnóstico de stack)
- `verify-ui` - opera a UI real (browser, TUI, template renderizado) para provar que uma mudança que toca tela de fato funciona, adicionando uma afirmação de fluxo operado com um artefato de screenshot ao mesmo relatório em `.claude/verification/` que o `verify-gate.py` confere; não serve para mudanças puras de backend/API sem superfície renderizada
- `skill-architect` - workflow guiado para autorar uma skill ou agent nova do jeito que este repo faz (CC-BY-4.0, adaptada de [tech-leads-club/agent-skills](https://github.com/tech-leads-club/agent-skills))
- `jury` - decide **entre opções concorrentes** com um painel de 3 a 5 subagents que argumentam sem ver o argumento um do outro, depois se compromete com um veredito preservando a dissidência e a suposição mais arriscada (CC-BY-4.0, adaptada de [tech-leads-club/agent-skills](https://github.com/tech-leads-club/agent-skills))
- `devils-advocate` - estressa uma spec/plan/decisão antes de assumir compromisso (advocacia do diabo, pre-mortem, red-team) (CC-BY-4.0, adaptada de [tech-leads-club/agent-skills](https://github.com/tech-leads-club/agent-skills))
- `diagnosing-bugs` - loop disciplinado de diagnóstico para bugs difíceis e regressões de performance; o gate é um loop de feedback apertado, capaz de dar red, antes de qualquer hipótese (MIT, adaptada de [mattpocock/skills](https://github.com/mattpocock/skills))
- `documenting-domains` - cria documentação local durável de domínio (arquivos CLAUDE.md aninhados) depois que uma feature vai ao ar (atribuição: [douglasgomes98](https://github.com/douglasgomes98))
- `postmortem` - postmortem sem culpados depois que um incidente termina (outage, vazamento entre tenants, deploy que falhou); tabela de severidade, linha do tempo, causas em camadas, mudanças preventivas confirmadas versus avaliadas, itens de ação com dono; escreve em `docs/postmortems/` (MIT, adaptada de [msitarzewski/agency-agents](https://github.com/msitarzewski/agency-agents))
- `skill-best-practices` - padrões de autoria para skills (frontmatter, progressive disclosure, descriptions)

> Skills específicas de stack (ex.: convenções de React SPA) **não** fazem parte do baseline — elas vêm de um plugin de stack no [njord marketplace](https://github.com/njord-app/marketplace), instalado por projeto (`/plugin install frontend-react@njord`).

### Subagents disponíveis

Os subagents em `baseline/agents/` rodam em janelas de contexto isoladas:

- `codebase-explorer` - arqueologia somente leitura; gera o repo map do zero em cada uso (sem cache, nada para ficar defasado), recorre a Grep/Glob para qualquer coisa mais estreita
- `spec-reviewer` - auditoria obrigatória do `spec.md` antes de virar um plan (`write-spec` a roda automaticamente)
- `code-reviewer` - revisa a implementação contra spec, plan, tasks e convenções; sob `/orchestrate` faz auto-gate uma vez por cluster, standalone faz auto-gate em cada fase (tem memória persistente). Achados carregam uma severidade (`blocker`/`should-fix`/`nit`/`pre-existing`) e um ID estável para que uma re-revisão convirja em vez de se repetir
- `reviewer` - review portátil de nível staff de um diff/branch inteiro; roda a verificação do repo e pode abrir o PR (se adapta a qualquer stack). Mesma taxonomia de severidade e mesmo contrato de convergência do `code-reviewer`, mas lê sua rodada anterior nos próprios comentários do PR (`gh pr view --comments`)
- `tester` - portátil; escreve e roda testes usando o framework próprio do repo, descoberto a partir do AGENTS.md/tooling
- `researcher` - investiga a fundo libs e APIs (memória persistente entre projetos)
- `security-auditor` - audita auth, secrets, validação de input
- `implementer` - **implementer portátil de fallback**: escreve código em qualquer stack aprendendo o repo antes (`AGENTS.md`, as rules, o código ao lado da mudança). Usado só quando não existe especialista de stack, e nomeia o especialista faltante no relatório para que a lacuna vá para o plugin em vez de ser pago em silêncio a cada vez

### Drivers (também skills)

Também são skills — `baseline/skills/<name>/SKILL.md` — mas elas *dirigem* um fluxo de vários passos na thread principal em vez de ensinar uma coisa só. Um arquivo command e uma skill produzem o mesmo `/name`, então são autorados como skills e nada depende de um caminho `commands/` pessoal:

- `orchestrate` - leva o `tasks.md` de uma spec até o fim: reconcilia as caixinhas contra o código, classifica cada task para escolher seus gates, agrupa-as em **alguns clusters coesos de 5 a 7 tasks** (um especialista por cluster, rodando em ordem — um agent por task é o que sai pior medido em qualquer eixo), pega aprovação, depois executa **uma wave por vez** (a wave inteira disparada numa única mensagem, coletada, buildada e testada uma vez com `verify-before-done` para a wave, depois `code-reviewer` **uma vez por cluster**, restrito aos arquivos daquele cluster), e abre um PR; para para um humano em qualquer coisa ambígua. Portátil (especialistas de stack vêm de um plugin). Veja `docs/workflows/feature-pipeline.md`.
- `lean` - a alternativa ao `orchestrate` para um modelo forte o bastante para sequenciar o próprio trabalho: um `plan.md` no lugar de `spec.md` mais `tasks.md` (problema, fluxo, o que muda, entidades/superfície tocada, portas sem volta, critérios de aceite), um `checks.md` pareando cada afirmação com sua prova, um único dispatch de especialista que constrói do jeito dele, um subagent novo que avalia cada afirmação e fecha com `verify-gate.py`, uma passada de `code-reviewer`, um PR. Mesmas paradas do `orchestrate` (ambiguidade, uma porta sem volta, uma branch protegida, um gate ainda vermelho depois de três tentativas). Use `orchestrate` em vez disso para um modelo mais fraco, uma trilha auditada de checkbox, ou uma mudança grande demais para o contexto de um especialista.
- `wave` - a metade de baixa cerimônia do `orchestrate`: dispara **um** lote de clusters coesos para especialistas em paralelo (uma única mensagem = concorrente, uma chamada por cluster), faz o gate uma vez, reporta, para. Sem spec, sem tabela de aprovação, sem PR. Use quando `orchestrate` for mais processo do que o trabalho merece.
- `handover` - handover de sessão compacto e de alto sinal (feito / estado atual / decisões abertas / não iniciado) para que uma sessão nova continue sem re-derivar o contexto. **Estado, não instrução** — descreve o que é verdade, nunca o que fazer a seguir, porque um fato sobrevive a uma instrução. **Reconcilia o `tasks.md` contra a realidade antes de escrever a narrativa, sempre escreve um arquivo** (`tasks.md § Handover`, ou `.claude/handovers/<date>-<slug>.md` quando nenhuma spec está ativa), imprime um bloco copiável, **e termina com um corte explícito** que nomeia esse arquivo — o estado está no disco, limpe a sessão e retome numa nova
- `checkpoint` - salvamento seguro: roda `verify-before-done`, depois commita e faz push do trabalho na branch de feature (nunca com um gate vermelho, nunca numa branch protegida)
- `status` - cartão somente leitura da saúde do projeto: spec/fase ativa, tasks não marcadas, status do gate, branch
- `harness-report` - relatório somente leitura sobre o **próprio harness**: quanto da implementação de fato é delegado, como os dispatches se distribuem, quantos ficam sem atribuição — julgado contra `.claude/docs/harness/harness-baseline.md`. Responde "isto está sendo usado do jeito que foi desenhado", pergunta que uma rule não consegue responder sobre si mesma

### Scripts disponíveis

A maior parte de `baseline/scripts/` dá suporte a um hook ou a uma skill e é descrita onde esse hook ou skill está (veja `baseline/scripts/README.md` para a lista completa). Alguns poucos são utilitários independentes que um repo ou um agent invoca direto, e diferente de um hook eles **não** são auto-registrados pelo `install-harness.sh`: rodar um é uma permissão que um repo que adota concede a si mesmo, uma vez, no próprio `.claude/settings.json` commitado:

- `env-set.sh` - faz upsert de UMA chave num arquivo estilo `.env` sem nunca imprimir o conteúdo do arquivo; o valor vem do STDIN, nunca de um argumento, então nunca cai no argv, no histórico do shell ou num transcript. Combina com `Bash(.claude/scripts/harness/env-set.sh:*)` liberado e `Read(.env)` mantido negado nas settings do repo que adota, então uma sessão consegue DEFINIR um secret sem nunca conseguir LER o arquivo. Veja a seção "Scripts com permissão própria" do ADOPTING.md para as linhas exatas de permissão e `baseline/scripts/README.md` para as garantias de segurança do script.

### Hooks registrados

Para este repo, em `.claude/settings.json`. Para um projeto que linkou o harness, `./install-harness.sh` registra os portáteis no `.claude/settings.local.json` daquele projeto, ignorado pelo git, apontando para caminhos absolutos neste checkout — o `settings.json` commitado do repo nunca é tocado. `protect-critical.sh` e `check-snapshot-on-session.sh` são **deliberadamente excluídos** do conjunto global: o primeiro conhece lockfiles e migrations, o segundo conhece um snapshot por repo, então os dois pertencem a um repo e não a uma máquina. `block-new-em-dashes.sh` é excluído por um motivo diferente: reforça uma preferência de estilo tipográfico DESTE repo, não uma convenção portátil, então `install-harness.sh` não a leva para um projeto que adota. `protect-harness.sh` e `protect-machine-config.sh` são o caso oposto e **estão** no conjunto global: o primeiro impede que uma sessão no projeto que adota alcance, por caminho absoluto, o checkout compartilhado do harness e desarme a guarda de que todo projeto depende; o segundo impede que uma sessão escreva config de nível máquina ou usuário (identidade git em `~/.gitconfig`, um rc file de shell) que fica fora de todo repo, então precisa ser registrado em todo lugar, não só aqui.

- `PreToolUse` no Bash: `block-secrets.sh` bloqueia comandos que leriam `.env` ou imprimiriam env vars com nome de secret
- `PreToolUse` no Bash: `protect-main.sh` bloqueia commits, pushes, merges em branches protegidas (main, master, etc), e bloqueia `gh pr merge --admin` **em qualquer lugar** — contornar a proteção de branch é decisão de um humano, não de um agent
- `PreToolUse` no Bash: `protect-unpushed.sh` bloqueia deletar trabalho que só existe localmente. `git branch -D`/`-d`/`--delete` numa branch (um delete `-r`/`--remotes` de uma ref de rastreio remoto local é isento, já que nunca perde trabalho) é bloqueado a menos que a branch não tenha commits fora dos seus remotos, ou que seu conteúdo já esteja na branch de integração, checado por conteúdo e não por ancestralidade, porque este repo faz squash-merge e `git branch --contains` dá falso negativo em toda branch que já foi ao ar. `git worktree remove`, mesmo com `--force`, é bloqueado quando o worktree carrega mudanças não commitadas, já que elas não existem em nenhum commit em lugar nenhum
- `PreToolUse` no Bash e no Edit/Write/MultiEdit: `protect-machine-config.sh` bloqueia escrever configuração git de nível máquina ou usuário: `git config --global`/`--system` (ou um `-f`/`--file` explícito apontando para `~/.gitconfig`, `~/.config/git/config` ou `/etc/gitconfig`) quando ESCREVE um valor, `--add`, `--unset`, `--unset-all`, `--replace-all`, `--edit`/`-e`, `--rename-section` ou `--remove-section`, além de escrever direto em `~/.gitconfig`, `~/.config/git/config`, `/etc/gitconfig`, `~/.zshrc`, `~/.bashrc`, `~/.bash_profile` ou `~/.profile` via Edit/Write. Uma leitura em qualquer escopo, e uma escrita local ao repo (sem flag de escopo, `--local`, `--worktree`), ambas passam. Escrito depois que o setup de fixture `git config --global user.name/user.email` de um agent sobrescreveu a identidade real de um mantenedor na máquina inteira, autorando 28 commits em cinco repos como `CI` antes que um check de verificação de autor de um provedor de deploy pegasse isso. A mensagem de bloqueio ensina o conserto: um `git -c user.name=... -c user.email=... commit ...` por invocação, `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`/`GIT_COMMITTER_*` para aquele comando específico, ou um `git config user.email ...` local ao repo
- `PreToolUse` no Bash e no Edit/Write: `log-edit.sh` acrescenta uma linha por escrita de arquivo em `.claude/tool-log.txt`, ignorado pelo git, registrando **qual thread** fez isso (principal ou especialista) — a matéria-prima para `/harness-report`. No Edit/Write ele lê `file_path` direto; no Bash ele recupera a escrita a partir do próprio comando (um redirect, `sed -i`, `tee`, `cp`, `mv`), registrando o alvo só quando resolve dentro do repo, e `?` quando o alvo é uma variável/substituição que não consegue resolver para um caminho literal em vez de descartar. Nunca bloqueia
- `PreToolUse` no Bash e no Edit/Write: `protect-critical.sh` bloqueia modificações em lockfiles, migrations aplicadas, código gerado, e outros arquivos críticos que pertencem ao repo (`.env`, `/secrets/`, `/dist/`, `/build/`, `/node_modules/`, etc), exceto arquivos terminados no literal `.example`. No Bash ele julga os mesmos caminhos alcançados via redirect, `sed -i`, `tee`, `cp`, `mv`, ou uma chamada `python3 -c`/heredoc `open(..., "w")`, usando o mesmo parser compartilhado do `log-edit.sh` (`baseline/hooks/lib/bash-write-targets.py`); um alvo que não consegue resolver para um caminho literal é ignorado, nunca bloqueado
- `PreToolUse` no Bash e no Edit/Write: `protect-harness.sh` bloqueia modificações na própria superfície de governança do harness — `.claude/settings.json`/`settings.local.json`, `baseline/hooks/*.sh`/`*.py`, `.claude/hooks/*.sh`/`*.py`, `baseline/rules/**`, `.claude/rules/**` (a metade `*.py` cobre o próprio `baseline/hooks/lib/bash-write-targets.py`, o parser compartilhado do qual este hook e o `protect-critical.sh` dependem para ver uma escrita feita via Bash; um padrão só de `.sh` teria deixado esse arquivo fora da própria superfície de governança deste hook) — seja a escrita vindo do Edit/Write ou do Bash (mesmo parser compartilhado do `protect-critical.sh` e do `log-edit.sh`). Uma regra decide todos eles, e o critério é a **revisabilidade**: uma edição num arquivo ignorado pelo git é bloqueada (ninguém nunca revisa isso, mesmo repo ou cross-repo), uma edição que alcança um CHECKOUT DE HARNESS (um repo cuja raiz tem tanto `install-harness.sh` quanto uma pasta `baseline/`, seu próprio ou de outro) a partir de um repo diferente é bloqueada independente de em qual repo a sessão começou (pela ADR 0003 do marketplace, um projeto consumidor linka direto na working tree de um checkout de harness, então essa edição ficaria ativa em todo lugar linkado sem commit e sem revisor), e uma edição num arquivo que vai aparecer no diff do PRÓPRIO repo, rastreado, ou novo e não ignorado, mesmo repo ou num projeto consumidor comum alcançado via cross-repo, é permitida. Mesma isenção de `.example`. É por isso que `settings.local.json` é recusado onde `settings.json` não é, e por que replicar uma mudança rastreada para o `.claude/settings.json` próprio de um projeto consumidor diferente, a partir de uma sessão com raiz aqui, agora passa: essa edição é revisada no diff e no PR do OUTRO projeto, exatamente como uma do mesmo repo
- `PreToolUse` no Edit/Write/MultiEdit: `block-new-em-dashes.sh` bloqueia uma edição de Markdown que aumentaria a contagem de em-dash do arquivo além do que era antes daquela chamada; editar ao lado de um em-dash já existente, ou remover um, ainda passa. É uma escolha de estilo só DESTE repo: está registrado aqui e em nenhum outro lugar, nem no conjunto portátil do `install-harness.sh` nem no `REPO_HOOKS` do `install.sh`, então um projeto que adota nunca herda isso
- `SessionStart`: `check-snapshot-on-session.sh` avisa se existir um snapshot do Repomix e ele estiver acima do orçamento de tamanho (nunca só por estar defasado, nada mais lê o arquivo automaticamente, veja `docs/decisions/0003-repo-map-over-snapshot.md`)
- `SessionStart`: `check-handover.sh` aponta uma sessão nova para o estado que uma anterior deixou no disco: avalia tanto o arquivo mais novo em `.claude/handovers/` quanto a seção `## Handover` do `tasks.md` da spec ativa, e aponta para o que for mais recente (empate no mesmo dia vai para a spec), citando o caminho do outro numa linha quando os dois existem. Emite só um ponteiro (caminho, data, tamanho, título), nunca o conteúdo do handover, via `hookSpecificOutput.additionalContext`. Fica em silêncio em `compact` (um resumo de compactação já carrega o estado da sessão) e sempre que não houver nada para apontar. Nunca bloqueia, sempre sai com 0
- `SessionStart`: `check-index.sh` avisa quando `CLAUDE.md` e a maquinaria (`baseline/`, `.claude/`, e `~/.claude/` só para nomes) ficam fora de sincronia — não listado, listado mas ausente, ou malformado (frontmatter ruim, nome/arquivo divergentes, hook sem `+x`). `--strict` sai com 1 para o CI. Qualquer caminho com um componente `*.pre-harness` e qualquer arquivo que o git considera ignorado ficam fora do scan, já que `install-harness.sh --adopt` deixa a cópia pré-migração no disco de propósito e um arquivo no gitignore (um snapshot gerado do Repomix, por exemplo) não é conteúdo autorado que se espera manter os ponteiros atualizados
- `SessionStart`: `check-baseline.sh` avisa quando seu checkout de harness está atrasado em relação ao remoto, ou tem edições **não commitadas** dentro de `baseline/` — essas ficam ativas em todo projeto na máquina, sem revisão. Não faz fetch e não fixa versão
- `SubagentStop`: `log-agent.sh` acrescenta uma linha de auditoria por execução de subagent em `.claude/agent-log.txt`, ignorado pelo git — tipo de agent, descrição da task, tokens, duração e contagem de tools, recuperados do próprio transcript do subagent quando o payload do hook os omite. Quando precisa adivinhar o transcript (só em clientes mais antigos), primeiro checa um pequeno registro "já cobrado", também ignorado pelo git, para que uma wave paralela nunca cobre os tokens do mesmo transcript duas vezes — um acerto repetido recebe o tipo de agent (ainda confiável) e `dup=1`, nunca uma métrica copiada

### Rules com escopo de path

Os arquivos em `baseline/rules/` carregam automaticamente com base no glob `paths:` deles, e caem em `.claude/rules/harness/` quando linkados num projeto — rules são descobertas recursivamente, então as rules próprias do repo coexistem ao lado delas. Uma rule de mesmo nome que o repo mantém direto em `.claude/rules/` não sobrepõe a linkada: as duas carregam, até que `install-harness.sh --adopt` remova a duplicata pondo a cópia do repo de lado (veja ADOPTING.md, seção 3, passo 5). Seis vêm com o template:

- `delegation.md` (casa com `**`, sempre carregada) - a thread principal coordena, especialistas implementam; nunca escreva código de feature na thread principal
- `resuming.md` (casa com `**`, sempre carregada) - onde procurar estado antes de re-derivá-lo quando o humano diz "continue" ou pergunta o que está pendente: o arquivo mais novo em `.claude/handovers/` (ou a seção `## Handover` da spec ativa), depois `tasks.md`, PRs abertos, `git log`/`git status`; um handover é estado datado para confirmar, não uma instrução para seguir de olhos fechados
- `specs.md` (casa com `specs/**`) - afirmações são verificadas contra código/git no momento de escrever, nunca copiadas de um texto já existente; uma spec escrita à mão ainda passa pelo `spec-reviewer`
- `git-workflow.md` (casa com `**`, sempre carregada) - nomenclatura de branch, Conventional Commits, convenções de PR, onde o trabalho acontece (local, worktree da ferramenta de agent, ou `spec-worktree`)
- `adr.md` (casa com `docs/decisions/**`) - Architecture Decision Records são só de acréscimo (append-only); supere, não reescreva
- `example-rule.md` - rule de exemplo mostrando o padrão para convenções com escopo de path

Veja `baseline/rules/example-rule.md` para a anatomia.

### Conhecimento só para IA

Documentação consultada só por agents (não por humanos) vive em `baseline/docs/`:

- `superpowers.md` - como o fluxo guiado por spec se integra com o plugin Superpowers
- `context-engineering.md` - disciplina de contexto que todo agent deve seguir (retornar conclusões, não material bruto; isolar trabalho pesado em subagents; externalizar estado; continuar agents em vez de redisparar)
- `dispatching.md` - como disparar: **se vale disparar de todo** e **quão fino cortar** (granularidade destrói qualidade; mais workers pode deixar a thread principal mais pesada; o ganho é orçamento de contexto, não velocidade); depois as seis formas de topologia (pipeline, fan-out/fan-in, pool de especialistas, produtor-revisor, supervisor, hierárquica) e como rodar cada uma com sub-agents; depois a mecânica - paralelo significa uma mensagem com várias chamadas de agent; background só para trabalho longo coletado neste turno; nunca colocar um gate em background; teto de concorrência; memória de agent
- `harness-baseline.md` - os números medidos contra os quais o harness é julgado (delegação 29%, participação de token da thread principal 71%, 1,0 dispatch por mensagem, de 22 sessões e 54 dispatches num projeto real), mais o que cada correção afirma e qual número confirmaria isso. Lido por `harness-report`
- `libs/` - como este projeto usa cada biblioteca externa (endpoints, pegadinhas, padrões específicos do projeto)

Para docs voltados a humanos (arquitetura, ADRs, runbooks, guias, patterns), veja `docs/`.
